Step 1

이번 커밋 한눈에 보기

이번 두 커밋에서 게시글 목록 페이지에 검색 기능을 추가했습니다.
사용자가 검색어를 입력하면 제목에 해당 키워드가 포함된 게시글만 목록에 표시됩니다.

핵심은 Spring Data JPA의 findByTitleContaining 메서드입니다.
SQL을 직접 작성하지 않아도 메서드 이름만으로 LIKE '%keyword%' 쿼리가 자동으로 생성됩니다.

또한 페이징 링크에 검색어를 함께 포함시켜, 다음 페이지로 이동해도 검색 결과가 유지되도록 했습니다.

첫 번째 커밋(검색 기능 1)에서 if/else 조건이 반대로 작성된 버그가 있었고,
두 번째 커밋(검색 기능 2)에서 이를 수정하고 HTML 검색 폼도 추가했습니다.

Step 2

무엇이 변경되었는가

BoardRepository.java

쿼리 메서드 findByTitleContaining이 추가되었습니다.
이 메서드 하나를 선언하는 것만으로 제목에 키워드가 포함된 게시글을 페이징 조회하는 기능이 완성됩니다.
SQL을 한 줄도 작성하지 않아도 되는 Spring Data JPA의 핵심 기능입니다.

BoardService.java

검색 전용 서비스 메서드 boardSearchList가 추가되었습니다.
Repository의 findByTitleContaining을 호출해서 결과를 반환합니다.
검색어가 없을 때 기존 boardList 메서드를 그대로 사용할 수 있도록 두 메서드를 분리했습니다.

BoardController.java

boardlist 메서드에 String searchKeyword 파라미터가 추가되었습니다.
사용자가 검색어를 입력하지 않으면 searchKeyword는 null이 되고, 전체 목록을 조회합니다.
검색어가 있으면 boardSearchList를 호출해 검색 결과를 조회합니다.

boardlist.html

두 가지 변경이 있었습니다.
첫째, 검색어를 입력하는 <form>이 추가되었습니다.
둘째, 페이징 링크에 searchKeyword 파라미터가 포함되어 페이지를 넘겨도 검색어가 유지됩니다.

Step 3

핵심 코드 설명

① BoardRepository — 쿼리 메서드

BoardRepository.java

Page<Board> findByTitleContaining(String searchKeyword, Pageable pageable);

이것이 이번 커밋 전체에서 가장 중요한 한 줄입니다.
메서드를 선언만 했는데 실제 SQL이 자동으로 만들어집니다.

Spring Data JPA는 메서드 이름을 분석합니다.

  • findBy → SELECT … WHERE
  • Title → title 컬럼
  • Containing → LIKE '%keyword%'

결국 아래 SQL이 실행됩니다.

실행되는 SQL

SELECT * FROM board WHERE title LIKE '%검색어%' ORDER BY id DESC LIMIT 10

메서드 이름 규칙: findBy + 필드명 + 조건 키워드

Containing이 필수가 아닙니다.
조건 키워드를 바꾸면 다른 SQL이 생성됩니다.

쿼리 메서드 종류

// 포함 검색 — LIKE '%keyword%'
findByTitleContaining(String keyword)

// 시작 검색 — LIKE 'keyword%'
findByTitleStartingWith(String keyword)

// 끝 검색 — LIKE '%keyword'
findByTitleEndingWith(String keyword)

// 정확히 일치 — WHERE title = 'keyword'
findByTitle(String title)

// OR 조건 — 제목 또는 내용에 포함
findByTitleContainingOrContentContaining(String title, String content)

// 크기 비교
findByIdGreaterThan(Integer id)

// 정렬 포함
findByTitleContainingOrderByIdDesc(String keyword)

필드명(Title, Content 등)은 Board 엔티티의 실제 필드명과 대소문자까지 맞춰야 합니다.

findById는 왜 Repository에 선언하지 않아도 되나?

JpaRepository를 상속받으면 자주 쓰는 메서드들이 기본으로 포함되어 있습니다.

JpaRepository 기본 제공 메서드

findById(ID id)       // 단건 조회
findAll()             // 전체 조회
findAll(Pageable p)   // 페이징 조회
save(T entity)        // 저장 / 수정
deleteById(ID id)     // 삭제
count()               // 개수
existsById(ID id)     // 존재 여부

이 메서드들은 어떤 프로젝트에서도 항상 필요하기 때문에 JpaRepository가 처음부터 제공합니다.
반면 findByTitleContaining은 어떤 컬럼으로 어떤 조건을 쓸지 프로젝트마다 다르기 때문에 직접 선언해야 합니다.

② BoardController — 파라미터 바인딩과 분기

BoardController.java

public String boardlist(Model model,
                        @PageableDefault(...) Pageable pageable,
                        String searchKeyword) {

    Page<Board> list = null;

    if (searchKeyword == null) {
        list = boardService.boardList(pageable);       // 전체 목록
    } else {
        list = boardService.boardSearchList(searchKeyword, pageable); // 검색 결과
    }
    ...
}

String searchKeyword는 URL 쿼리 파라미터 ?searchKeyword=xxx를 자동으로 받아줍니다.
@RequestParam 없이도 Spring MVC가 이름이 같으면 자동으로 연결해줍니다.
검색어가 없으면 null이 들어오고, 검색어가 있으면 문자열이 들어옵니다.

버그와 수정 과정

검색 기능 1 커밋에서 조건이 반대로 작성되었습니다.
if (searchKeyword != null)일 때 전체 목록을, else일 때 검색 결과를 조회하는 코드였습니다.
이 상태에서는 검색어가 있으면 전체 목록이, 검색어가 없으면 null을 boardSearchList에 넘겨 오류가 납니다.

검색 기능 2 커밋에서 != null을 == null로 수정해 올바르게 동작하게 했습니다.
이런 조건 반전 버그는 매우 흔합니다. 코드를 짜고 나면 if/else 조건을 한 번 더 확인하는 습관을 들이세요.

③ boardlist.html — 검색 폼과 검색어 유지

boardlist.html

<!-- 페이징 링크에 searchKeyword를 함께 전달 -->
<a th:if="${page != nowPage}"
   th:href="@{/board/list(page=${(page-1)}, searchKeyword = ${param.searchKeyword})}"
   th:text="${page}"></a>

<!-- 검색 폼 -->
<form th:action="@{/board/list}" method="get">
    <input type="text" name="searchKeyword">
    <button type="submit">검색</button>
</form>

${param.searchKeyword}는 현재 페이지의 URL에서 searchKeyword 파라미터를 읽어옵니다.
이것을 페이징 링크에 포함시키면 2페이지, 3페이지로 이동해도 검색어가 사라지지 않습니다.

검색 폼의 name="searchKeyword"는 Controller의 String searchKeyword 파라미터 이름과 반드시 일치해야 합니다.
이름이 같아야 Spring이 자동으로 연결해줍니다.

param.searchKeyword 대신 model.addAttribute를 써도 되나?

됩니다. 둘 다 동작합니다.

model.addAttribute 방식 (대안)

// BoardController.java
model.addAttribute("searchKeyword", searchKeyword);
<!-- boardlist.html -->
searchKeyword = ${searchKeyword}

차이는 데이터가 어디서 오는가입니다.
${param.searchKeyword}는 Thymeleaf가 현재 URL의 쿼리 파라미터를 직접 읽습니다. Controller를 거치지 않습니다.
model.addAttribute는 Controller가 명시적으로 값을 넘겨줍니다.

결과는 같지만 param을 쓰면 Controller에 코드를 추가하지 않아도 되어 더 간결합니다.

@{/board/list(page=..., searchKeyword=...)} 로 URL이 어떻게 만들어지나?

Thymeleaf의 @{경로(key=value, key=value)} 문법은 괄호 안의 값을 자동으로 쿼리스트링으로 붙여줍니다.

예를 들어 현재 URL이 /board/list?searchKeyword=Spring이고 3페이지 링크라면:

생성되는 URL

/board/list?page=2&searchKeyword=Spring

검색어 없이 접근한 경우 param.searchKeyword가 null이므로:

/board/list?page=2

null인 파라미터는 Thymeleaf가 URL에 포함시키지 않습니다. searchKeyword=가 사라집니다.

Step 4

왜 이렇게 작성했는가

왜 SQL을 직접 작성하지 않고 findByTitleContaining을 쓰는가?

BoardRepository.java

Page<Board> findByTitleContaining(String searchKeyword, Pageable pageable);

SQL을 직접 작성하면 아래처럼 @Query를 붙여야 합니다.

BoardRepository.java — @Query 방식 (대안)

@Query("SELECT b FROM Board b WHERE b.title LIKE %:keyword%")
Page<Board> searchByTitle(String keyword, Pageable pageable);

두 방법 모두 동일하게 동작합니다.
하지만 단순한 검색 조건이라면 메서드 이름 규칙을 따르는 것이 코드가 훨씬 짧고 읽기 쉽습니다.
복잡한 조건(여러 컬럼, OR 조건, 동적 쿼리 등)이 필요할 때는 @Query나 Querydsl을 씁니다.

왜 boardSearchList라는 메서드를 Service에 따로 만들었는가?

BoardService.java

public Page<Board> boardSearchList(String searchKeyword, Pageable pageable) {
    return boardRepository.findByTitleContaining(searchKeyword, pageable);
}

Controller에서 boardRepository.findByTitleContaining(...)을 직접 호출할 수도 있습니다.
하지만 그렇게 하면 Controller가 Repository에 직접 의존하게 됩니다.
Service 메서드를 하나 두면 나중에 검색 로직이 복잡해져도(예: 제목+내용 동시 검색) Controller 코드를 건드리지 않아도 됩니다.
역할을 분리해두면 변경이 생겼을 때 영향 범위가 좁아집니다.

왜 null 체크로 분기하는가?

BoardController.java

Page<Board> list = null;

if (searchKeyword == null) {           // ← 이 if문이 "null 체크"
    list = boardService.boardList(pageable);              // A 경로: 전체 목록
} else {
    list = boardService.boardSearchList(searchKeyword, pageable); // B 경로: 검색 결과
}

분기란 if/else로 실행 경로가 두 갈래로 나뉜다는 뜻입니다.
searchKeyword가 null이면 A 경로(전체 목록), 값이 있으면 B 경로(검색 결과)를 탑니다.

그렇다면 왜 null을 기준으로 나누는가?
사용자가 그냥 /board/list로 접근하면 URL에 searchKeyword 파라미터가 아예 없습니다.
이 경우 Spring은 searchKeyword에 null을 넣어줍니다.
반대로 검색 폼에 "Spring"을 입력하면 URL이 /board/list?searchKeyword=Spring이 되고, "Spring"이 들어옵니다.
즉 null 여부가 "검색한 상황인가 아닌가"를 구분하는 기준이 됩니다.

왜 페이징 링크에 searchKeyword를 포함시키는가?

boardlist.html

<!-- 변경 전 -->
<a th:href="@{/board/list(page=${(page-1)})}" th:text="${page}"></a>

<!-- 변경 후 -->
<a th:href="@{/board/list(page=${(page-1)}, searchKeyword = ${param.searchKeyword})}" th:text="${page}"></a>

searchKeyword를 포함하지 않으면 2페이지 링크가 /board/list?page=1이 됩니다.
Controller에는 searchKeyword가 없으므로 null이 들어오고, 검색 결과 대신 전체 목록이 나옵니다.
"Spring"으로 검색한 뒤 2페이지를 눌렀는데 갑자기 전체 목록이 나오면 매우 불편합니다.

${param.searchKeyword}는 현재 URL에서 searchKeyword 값을 읽어서 링크에 그대로 실어줍니다.
덕분에 /board/list?page=1&searchKeyword=Spring처럼 검색어가 유지됩니다.

Step 6

이전 커밋과 비교

이전 커밋 (페이징 처리)

Controller
  ↓ pageable만 전달
Service
  ↓ boardList(pageable)
Repository
  ↓ findAll(pageable)
DB → 전체 목록 반환

HTML 페이징 링크:
  page 파라미터만 포함

현재 커밋 (검색 기능 추가)

Controller
  ↓ + searchKeyword 파라미터
null → boardList
값 있음 → boardSearchList
Service
  ↓ + boardSearchList 메서드
Repository
  ↓ + findByTitleContaining
DB → 조건부 조회

HTML 페이징 링크:
  + searchKeyword 파라미터 포함

이전 커밋까지는 항상 전체 게시글을 조회했습니다.
이번 커밋으로 검색어 유무에 따라 다른 쿼리를 실행하는 분기 로직이 생겼습니다.
Repository → Service → Controller 순서로 각 계층에 변경이 생긴 것을 확인할 수 있습니다.

Step 7

초보자가 하기 쉬운 착각

findByTitleContaining은 직접 만든 메서드가 아닌가?

선언은 우리가 했지만, 실제 구현(SQL 실행)은 Spring Data JPA가 합니다.
인터페이스에 메서드 이름만 선언하면 Spring이 이름을 분석해서 쿼리를 만들고 실행해줍니다.
우리가 메서드 바디를 작성하지 않아도 됩니다.

@RequestParam 없이도 파라미터가 연결된다?

Spring MVC는 메서드 파라미터 이름이 HTTP 파라미터 이름과 같으면 @RequestParam 없이도 자동으로 연결합니다.
단, Java 컴파일 옵션에 따라 파라미터 이름이 보존되지 않는 경우가 있습니다.
그런 경우에는 @RequestParam("searchKeyword") String searchKeyword처럼 명시하는 것이 안전합니다.

검색어가 없으면 빈 문자열("")이 들어온다?

아닙니다. URL에 ?searchKeyword 파라미터 자체가 없으면 null이 들어옵니다.
검색 폼에서 아무것도 입력하지 않고 검색 버튼을 누르면 ?searchKeyword=처럼 빈 문자열이 전달됩니다.
이 경우 searchKeyword는 null이 아닌 ""(빈 문자열)이 되어 LIKE '%%' 쿼리가 실행됩니다.
실무에서는 빈 문자열 처리도 추가하는 것이 좋습니다.

Containing이 포함 검색이라는 게 SQL에서는 어떻게 동작하나?

SQL LIKE 연산자는 %를 와일드카드(어떤 문자든 허용)로 사용합니다.
Containing은 앞뒤 모두 %를 붙인 LIKE '%keyword%'가 됩니다.
StartingWith는 LIKE 'keyword%', EndingWith는 LIKE '%keyword'입니다.

Step 8

중요도 구분

🔴 반드시 이해

  • Spring Data JPA 쿼리 메서드 이름 규칙
  • findByTitleContaining → LIKE '%…%'
  • Controller에서 String 파라미터로 쿼리스트링 받기
  • null 체크로 검색/전체 분기
  • 검색어를 페이징 링크에 포함시키는 이유

🟡 개념만 이해

  • param.searchKeyword의 의미
  • StartingWith / EndingWith 등 다른 쿼리 메서드
  • @RequestParam 어노테이션

🟢 나중에 공부

  • @Query 어노테이션으로 JPQL 직접 작성
  • Querydsl 동적 쿼리
  • 전문 검색(Full-text search)
  • LIKE 검색의 인덱스 미적용 문제
Step 9

오늘 배운 것

  • Spring Data JPA는 메서드 이름을 분석해서 SQL 쿼리를 자동으로 생성한다.
  • findByTitleContaining은 WHERE title LIKE '%keyword%'로 변환된다.
  • Controller 메서드에서 파라미터 이름과 HTTP 쿼리 파라미터 이름이 같으면 자동으로 연결된다.
  • 파라미터가 없으면 null이 들어오므로, null 체크로 검색/전체 조회를 분기할 수 있다.
  • Thymeleaf에서 ${param.파라미터명}으로 현재 URL의 쿼리 파라미터를 읽을 수 있다.
  • 페이징 링크에 검색어를 포함시켜야 페이지를 이동해도 검색 결과가 유지된다.
  • if/else 조건의 방향을 반드시 확인해야 한다. 조건 반전 버그는 매우 흔하다.
Step 10

이해도 확인 질문

  1. findByTitleContaining을 인터페이스에 선언만 했는데 동작하는 이유는?

    Spring Data JPA가 메서드 이름을 파싱해서 LIKE '%keyword%' 쿼리를 자동 생성하고, 프록시 객체를 통해 실행합니다. 인터페이스 구현체는 Spring이 런타임에 만들어줍니다.

  2. 사용자가 검색어 없이 /board/list에 접근했을 때 searchKeyword에 어떤 값이 들어오는가?

    null이 들어옵니다. URL에 searchKeyword 파라미터 자체가 없으므로 Spring은 null을 할당합니다. 이 경우 if (searchKeyword == null) 분기로 전체 목록을 반환합니다.

  3. 페이징 링크에 searchKeyword = ${param.searchKeyword}를 추가하지 않으면 어떤 문제가 생기는가?

    "Spring"으로 검색한 뒤 2페이지를 눌렀을 때 URL에 searchKeyword가 없어 Controller에 null이 전달됩니다. 그러면 전체 목록이 조회되어 검색 결과가 사라집니다.

  4. 검색 기능 1 커밋의 버그는 무엇이었고, 어떻게 수정했는가?

    if (searchKeyword != null) 일 때 boardList(전체 목록)를, else일 때 boardSearchList(검색)를 호출했습니다. 조건이 반대였습니다. 검색 기능 2에서 != null을 == null로 수정해 올바르게 동작하게 했습니다.

  5. Controller에서 Repository를 직접 호출하지 않고 Service를 거치는 이유는?

    역할 분리를 위해서입니다. Service에 비즈니스 로직을 모아두면 나중에 검색 조건이 복잡해져도 Controller 코드를 변경하지 않아도 됩니다. 변경의 영향 범위를 좁히는 것이 핵심입니다.
