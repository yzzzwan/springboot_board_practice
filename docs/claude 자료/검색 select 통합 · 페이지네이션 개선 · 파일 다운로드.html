Step 3

핵심 코드 설명

① String 비교: == vs .equals()

BoardController.java

// 이전
if(searchOption == "Total") { ... }

// 이후
if("Total".equals(searchOption)) { ... }

Java에서 ==는 두 변수가 메모리상 같은 객체를 가리키는지를 비교합니다.
반면 .equals()는 문자열 내용이 같은지를 비교합니다.

HTTP 요청으로 들어온 searchOption은 새로 생성된 String 객체이기 때문에,
코드에 직접 쓴 "Total"과 주소가 달라서 ==로는 항상 false가 됩니다.

⚠ 왜 우연히 맞을 수도 있다고 하는가?

Java는 String Pool이라는 메모리 영역에 동일한 문자열 리터럴을 재사용합니다.
코드에서 직접 "Total"을 두 번 쓰면 같은 객체를 가리켜서 ==가 맞습니다.
하지만 HTTP 요청으로 들어온 문자열은 Pool 밖에서 생성되므로 보장되지 않습니다.

"Total".equals(searchOption)처럼 리터럴을 앞에 두는 이유는,
searchOption이 null이어도 NullPointerException이 나지 않기 때문입니다.

② select → Controller 파라미터 흐름

boardlist.html

<form th:action="@{/board/list}" method="get">
    <select name="searchOption">
        <option value="Total" th:selected="${searchOption == 'Total'}">통합검색</option>
        <option value="Title" th:selected="${searchOption == 'Title'}">제목</option>
        <option value="Content" th:selected="${searchOption == 'Content'}">내용</option>
    </select>
    <input type="text" name="searchKeyword" th:value="${searchKeyword}">
    <button type="submit">검색</button>
</form>

form이 submit되면 브라우저는 name=value 쌍을 URL에 붙여 보냅니다.
예를 들어 "제목"을 선택하고 "스프링"을 입력하면:

HTTP 요청

GET /board/list?searchOption=Title&searchKeyword=스프링

Controller는 파라미터 이름이 일치하면 자동으로 받습니다.

BoardController.java

public String boardlist(Model model,
                        Pageable pageable,
                        String searchOption,   // "Title"
                        String searchKeyword){ // "스프링"

th:selected="${searchOption == 'Total'}"는 검색 후 페이지가 다시 렌더링될 때,
Controller가 Model에 넣어준 searchOption 값에 맞춰 드롭다운 선택 상태를 복원합니다.

⚠ th:selected 의 비교식 위치 주의

th:selected="${searchOption} == 'Total'"은 잘못된 방식입니다.
${} 밖에서 비교하면 Thymeleaf가 제대로 평가하지 않습니다.
반드시 th:selected="${searchOption == 'Total'}" — 달러 중괄호 안에서 비교해야 합니다.

③ 페이지네이션 범위 계산

BoardController.java — 이전

int startPage = Math.max(nowPage - 4, 1);
int endPage   = Math.min(nowPage + 5, list.getTotalPages());

BoardController.java — 이후

int startPage = Math.min(Math.max(nowPage - 2, 1), (list.getTotalPages() - 5) + 1);
int endPage   = Math.max(Math.min(nowPage + 2, list.getTotalPages()), 5);

이전 방식은 현재 페이지가 5페이지면 1~10, 6페이지면 2~11처럼 비대칭적으로 늘어났습니다.
개선 후에는 현재 페이지를 기준으로 좌우 2칸씩, 총 5개의 페이지 번호가 보입니다.

④ ResponseEntity<Resource> — 파일 다운로드 핵심

이 부분을 처음 보면 낯선 타입이 많이 등장합니다. 하나씩 분해해서 설명합니다.

BoardController.java

@GetMapping("/board/download/{id}")
public ResponseEntity<Resource> download(@PathVariable Integer id) throws Exception {
    Board board = boardService.boardView(id);

    String projectPath = System.getProperty("user.dir") + "\\src\\main\\resources\\static\\files";
    Path filePath = Path.of(projectPath, board.getFilename());

    Resource resource = new FileSystemResource(filePath);

    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION,
                    "attachment; filename=\"" + board.getOriginal_filename() + "\"")
            .body(resource);
}

@PathVariable이란?
URL 경로 안의 {id} 값을 메서드 파라미터로 꺼내오는 어노테이션입니다.
@RequestParam은 어노테이션을 생략해도 파라미터 이름으로 자동 매핑되지만,
@PathVariable은 생략하면 Spring이 경로 변수와 파라미터를 연결하지 못합니다.

BoardController.java — 대안 방식

// ❌ @PathVariable 없으면 id = null
@GetMapping("/board/download/{id}")
public ResponseEntity<Resource> download(Integer id) { ... }

// ✅ 반드시 @PathVariable 필요
@GetMapping("/board/download/{id}")
public ResponseEntity<Resource> download(@PathVariable Integer id) { ... }

또한 파라미터 이름이 {id}와 일치해야 자동으로 매핑됩니다.
이름을 다르게 쓰고 싶다면 @PathVariable("id")처럼 명시해야 합니다.

BoardController.java — 이름이 다를 때

// boardId라는 이름을 쓰고 싶을 때
@GetMapping("/board/download/{id}")
public ResponseEntity<Resource> download(@PathVariable("id") Integer boardId) { ... }

{id}에 Integer가 아닌 값이 들어오면?
예를 들어 /board/download/abc로 요청하면 Spring이 "abc"를 Integer로 변환하다 실패해
400 Bad Request 에러가 발생합니다. 사용자가 직접 URL을 조작하지 않는 한 실제로 발생하지 않습니다.

그러면 /board/list처럼 id가 없는 경우는?
/board/list는 Path Variable이 없고 ?searchKeyword=스프링처럼 Query Parameter를 사용합니다.
Query Parameter는 없으면 null이 들어오고 에러가 나지 않습니다.
그래서 StringUtils.hasText(searchKeyword)로 null 체크를 하는 것입니다.

방식 URL 예시 없을 때
Path Variable /board/download/5 URL 자체가 매칭 안 되어 400 에러
Query Parameter /board/list?searchKeyword=스프링 null로 들어옴, 에러 없음

ResponseEntity란?
지금까지 Controller 메서드는 String을 반환해서 어떤 HTML을 보여줄지 알려줬습니다.
ResponseEntity는 그것과 다릅니다. HTML을 보여주는 게 아니라 HTTP 응답 전체를 직접 만드는 객체입니다.
상태코드 + 헤더 + 본문(body)을 모두 직접 제어할 수 있습니다.

ResponseEntity<Resource>에서 Resource는 body에 담길 내용의 타입입니다.
파일을 body로 보내기 때문에 Resource를 씁니다.

Resource란?
org.springframework.core.io.Resource는 Spring이 파일, URL, 클래스패스 등
다양한 "자원"을 통일된 방식으로 다루기 위해 만든 인터페이스입니다.
실제 파일을 읽을 때는 그 구현체인 FileSystemResource를 사용합니다.

BoardController.java

Resource resource = new FileSystemResource(filePath);

디스크의 파일 경로를 Spring이 읽을 수 있는 Resource 객체로 감싸는 것입니다.
Spring은 이 객체를 받아서 파일 내용을 HTTP 응답 body에 바이트 단위로 실어 보냅니다.

Content-Disposition 헤더란?
브라우저에게 "이 파일을 어떻게 처리해라"고 지시하는 HTTP 헤더입니다.

헤더 값 브라우저 동작
inline 브라우저가 파일을 직접 열어서 보여줌 (이미지, PDF 등)
attachment 브라우저가 파일을 저장 대화상자를 열어 다운로드함

BoardController.java

.header(HttpHeaders.CONTENT_DISPOSITION,
        "attachment; filename=\"" + board.getOriginal_filename() + "\"")

attachment로 지정했기 때문에 브라우저는 파일을 열지 않고 저장합니다.
filename= 뒤에 original_filename을 넣었기 때문에, UUID가 붙은 서버 파일명이 아닌
사용자가 업로드한 원본 파일명으로 저장됩니다.

ResponseEntity.ok().header(...).body(...) 구조
메서드 체이닝으로 응답을 조립하는 방식입니다.

BoardController.java — 풀어서 보면

// ResponseEntity.ok() → 상태코드 200 OK 설정
// .header(이름, 값)   → HTTP 헤더 추가
// .body(resource)     → 응답 본문에 파일 내용 삽입

return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"파일명\"")
        .body(resource);
⭐ 현업 포인트

현업에서 파일 다운로드 엔드포인트는 대부분 이 구조를 그대로 씁니다.
바뀌는 건 filename 인코딩 처리 정도입니다 (한글 파일명은 인코딩이 필요합니다).
이 패턴을 익혀두면 어떤 프로젝트에서도 바로 응용할 수 있습니다.

💡 개선 포인트 — 한글 파일명 깨짐

현재 코드는 파일명을 그냥 문자열로 넣기 때문에 한글 파일명이 깨질 수 있습니다.
실무에서는 URL 인코딩 처리가 필요합니다.

import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

String encodedName = URLEncoder.encode(board.getOriginal_filename(), StandardCharsets.UTF_8);
.header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"" + encodedName + "\"")
Step 4

왜 이렇게 작성했는가?

왜 String 비교에 .equals()를 쓰는가?

BoardController.java

if("Total".equals(searchOption)) { ... }

Java의 ==는 주소 비교입니다.
HTTP 요청으로 들어온 문자열은 새로 생성된 객체라서, 코드에 쓴 "Total"과 주소가 다릅니다.
내용이 같아도 ==는 false를 반환하기 때문에 검색이 동작하지 않습니다.
.equals()는 주소가 아닌 내용을 비교하므로 항상 올바르게 동작합니다.

왜 페이지네이션 링크에 searchOption을 포함해야 하는가?

boardlist.html

<a th:href="@{/board/list(page=${page-1}, searchKeyword=${searchKeyword}, searchOption=${searchOption})}">

페이지 번호를 클릭하면 Controller에 새 GET 요청이 전송됩니다.
URL에 searchOption이 없으면 Controller는 searchOption=null로 받고,
"Total".equals(null)은 false이므로 어떤 분기도 타지 않아 전체 목록이 나옵니다.
검색 상태를 유지하려면 페이지 이동 URL에 검색 조건을 함께 실어 보내야 합니다.

왜 파일 다운로드를 별도 엔드포인트로 만드는가?

BoardController.java

@GetMapping("/board/download/{id}")
public ResponseEntity<Resource> download(@PathVariable Integer id) { ... }

이전 방식은 파일 경로(/files/uuid_파일명.jpg)를 링크로 직접 연결했습니다.
그러면 브라우저가 판단해서 이미지나 PDF는 그냥 열어버립니다 (다운로드 안 됨).
또한 UUID가 붙은 파일명으로 저장됩니다.

별도 엔드포인트를 만들면 Content-Disposition: attachment 헤더로 강제 다운로드하고,
original_filename을 이용해 원본 파일명으로 저장되게 할 수 있습니다.

왜 다운로드는 Controller에서 처리하고 Service를 만들지 않는가?

Service는 비즈니스 로직(규칙, 계산, 트랜잭션)을 담당합니다.
파일 다운로드는 "파일 경로를 찾아 HTTP 응답에 담아 보내는 것"으로,
비즈니스 규칙이 아닌 HTTP 응답 구성에 해당합니다.
DB에서 Board를 꺼내는 건 이미 있는 boardService.boardView(id)를 재사용하면 충분합니다.

Step 7

초보자가 하기 쉬운 착각

⚠ "String == 비교가 때로는 되니까 써도 된다"

String Pool 때문에 컨트롤러 내부 로직에서는 우연히 맞을 수 있습니다.
하지만 HTTP 요청으로 받은 파라미터는 보장되지 않습니다.
Java에서 String 비교는 항상 .equals()를 씁니다. 예외가 없습니다.

⚠ "select에서 선택한 텍스트가 서버로 간다"

<option value="Title">제목</option>에서 서버로 전송되는 건 "제목"이 아니라 "Title"입니다.
value 속성 값이 전송되고, 태그 안 텍스트는 화면에 보여주는 용도입니다.

⚠ "ResponseEntity를 반환하면 항상 파일이 다운로드된다"

ResponseEntity 자체는 그냥 HTTP 응답을 만드는 객체입니다.
파일이 다운로드되는 건 Content-Disposition: attachment 헤더 때문입니다.
이 헤더가 없으면 파일을 보내더라도 브라우저가 열어버릴 수 있습니다.

⚠ "FileSystemResource가 파일을 직접 복사해서 보낸다"

FileSystemResource는 파일을 읽기 위한 참조(포인터)를 만드는 것입니다.
Spring이 이 객체를 받아서 HTTP 응답 body에 바이트를 스트리밍합니다.
우리 코드에서 파일을 직접 읽거나 byte[]로 변환하지 않아도 됩니다.

Step 8

중요도 구분

🔴 반드시 이해

  • String은 .equals()로 비교
  • select의 name이 파라미터 이름, value가 파라미터 값
  • th:selected로 드롭다운 상태 복원
  • 페이지 이동 링크에 검색 조건 포함
  • ResponseEntity로 HTTP 응답 직접 제어
  • Content-Disposition: attachment = 강제 다운로드

🟡 개념만 이해

  • Resource 인터페이스 역할
  • FileSystemResource가 파일 경로를 감싸는 것
  • 페이지 범위 Math.max/min 중첩
  • String Pool 개념

🟢 나중에 공부

  • 한글 파일명 URL 인코딩
  • 대용량 파일 청크 스트리밍
  • 파일 접근 권한 제어
  • HTTP/1.1 Content-Disposition 스펙 전체
Step 9

오늘 배운 것

  • Java에서 String 비교는 반드시 .equals()를 사용한다. ==는 주소 비교다.
  • <select name="X">에서 선택된 <option value="Y">는 X=Y로 서버에 전달된다.
  • th:selected="${변수 == '값'}"으로 드롭다운 선택 상태를 복원할 수 있다.
  • 페이지 이동 링크에 검색 조건을 포함하지 않으면 검색 상태가 초기화된다.
  • ResponseEntity는 상태코드, 헤더, 본문을 모두 직접 제어하는 HTTP 응답 객체다.
  • Content-Disposition: attachment 헤더가 브라우저에게 파일을 저장하게 지시한다.
  • FileSystemResource는 디스크의 파일을 Spring이 읽을 수 있는 형태로 감싸는 클래스다.
Step 10

이해도 확인 질문

  • Java에서 searchOption == "Total"이 항상 동작하지 않는 이유는?

    HTTP 요청으로 전달된 searchOption은 새로 생성된 String 객체다. ==는 주소를 비교하기 때문에, 코드에 쓴 "Total" 리터럴과 주소가 달라 false가 된다. 내용 비교는 .equals()를 써야 한다.

  • <option value="Title">제목</option>에서 서버로 전송되는 값은 무엇인가?

    "Title"이다. value 속성 값이 전송된다. "제목"이라는 텍스트는 화면에 보여주는 용도이며 서버로 가지 않는다.

  • 페이지 이동 링크에 searchOption을 포함하지 않으면 어떤 일이 생기는가?

    Controller에 searchOption=null로 전달된다. null은 어떤 조건도 만족하지 않아 전체 목록이 나오고, 검색 결과가 사라진다.

  • ResponseEntity는 무엇이며, 일반 Controller 메서드의 String 반환과 무엇이 다른가?

    ResponseEntity는 HTTP 응답 전체(상태코드 + 헤더 + 본문)를 직접 구성하는 객체다. String 반환은 어떤 HTML 뷰를 렌더링할지 Thymeleaf에게 알려주는 것이고, ResponseEntity는 HTML이 아닌 파일, JSON 등 어떤 데이터든 HTTP 응답으로 직접 보낼 수 있다.

  • Content-Disposition: inline과 attachment의 차이는?

    inline은 브라우저가 파일을 직접 열어서 보여주고(이미지, PDF 등), attachment는 파일 저장 대화상자를 열어 다운로드한다. 이번 커밋에서는 attachment를 사용해서 어떤 파일이든 강제 다운로드하게 했다.
