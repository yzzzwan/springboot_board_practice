Step 1

이번 Commit 한눈에 보기

이번 commit에서는 게시글을 작성할 때 이미지 등의 파일을 첨부할 수 있는 기능을 만들었습니다.

글쓰기 폼에 파일 선택창(input type="file")을 추가하고, 폼이 파일을 전송할 수 있도록 enctype을 바꿨습니다.

서버에서는 전달받은 파일을 고유한 이름으로 바꿔 프로젝트의 static/files 폴더에 저장하고, 그 파일의 이름과 경로를 Board 엔티티에 함께 저장합니다.

실제 파일 데이터는 파일시스템에, 파일을 찾아가는 경로만 DB에 남기는 구조입니다. 게시글 상세 화면에는 이 경로를 이용한 다운로드 버튼도 추가되었습니다.

BoardService.java — 파일 저장 로직 추가

public void boardWrite(Board board, MultipartFile file) throws Exception{
    String projectPath = System.getProperty("user.dir") + "\\src\\main\\resources\\static\\files";
    UUID uuid = UUID.randomUUID();
    String fileName = uuid + "_" + file.getOriginalFilename();
    File saveFile = new File(projectPath, fileName);
    file.transferTo(saveFile);

    board.setFilename(fileName);
    board.setFilepath("/files/" + fileName);

    boardRepository.save(board);
}

Step 3

핵심 코드 설명

enctype="multipart/form-data"

<form action="/board/writepro" method="post" enctype="multipart/form-data">

초보자 관점

보통의 폼은 글자만 담긴 편지봉투라면, 파일을 넣으려면 소포 상자로 바꿔야 합니다. enctype="multipart/form-data"가 그 "소포 상자"입니다.

Java / Spring 관점

기본 폼 인코딩(application/x-www-form-urlencoded)은 텍스트만 key=value로 이어붙여 보낼 수 있습니다. 파일 같은 바이너리 데이터는 이 방식으로 보낼 수 없기 때문에, 요청 전체를 여러 "부분(part)"으로 쪼개 보내는 멀티파트 방식이 필요합니다. Spring Boot는 이 요청을 자동으로 감지해서 MultipartResolver가 파싱을 대신 처리해줍니다.

multipart/form-data는 언제 필요한가?

태그 종류가 기준이 아니라 바이너리 데이터가 폼에 섞이는지가 기준입니다. <input type="file">이 하나라도 있으면 필요하고, text, checkbox, date, select, textarea 등은 전부 기본 인코딩으로 충분합니다.
<input type="file" multiple>로 여러 파일을 올릴 때도 여전히 multipart이며, 파일마다 Part가 하나씩 늘어날 뿐입니다.
<form> 없이 JavaScript fetch/XMLHttpRequest로 FormData에 File/Blob을 담아 보낼 때도, 브라우저가 자동으로 multipart로 인코딩해줍니다(이 경우 enctype 속성 자체가 없어도 됩니다).

초보자 관점

업로드된 파일을 다루기 쉽게 포장해둔 "택배 상자"라고 생각하면 됩니다. 원본 파일명, 파일 크기, 실제 내용을 모두 가지고 있습니다.

Java 관점

MultipartFile은 인터페이스입니다. 개발자가 직접 구현하지 않아도, Spring이 요청의 file이라는 이름의 Part를 찾아 구현체 객체를 만들어 자동으로 주입해줍니다.

Part란 무엇인가?

multipart 요청 하나는 boundary라는 구분선으로 나뉜 여러 조각으로 구성되는데, 그 조각 하나하나를 Part라고 부릅니다. 텍스트 필드도 Part고, 파일도 Part입니다. 실제 요청 본문은 대략 이런 모습입니다.

------WebKitFormBoundaryABC123
Content-Disposition: form-data; name="title"

제목입니다
------WebKitFormBoundaryABC123
Content-Disposition: form-data; name="file"; filename="사진.jpg"
Content-Type: image/jpeg

(여기부터 실제 이미지 바이너리 데이터)
------WebKitFormBoundaryABC123--

파일이 담긴 Part만 filename과 Content-Type을 추가로 가집니다. 서블릿 표준에는 이 조각을 표현하는 jakarta.servlet.http.Part 인터페이스가 있고, Spring은 그 중 filename이 있는(=파일인) Part를 더 쓰기 편한 MultipartFile로 감싸서 넘겨주는 것입니다. 즉 "file이라는 이름의 Part를 찾는다"는 말은, 여러 Part 중 name="file"인 조각을 찾아 매칭한다는 뜻입니다.

Spring 관점

HTML의 <input type="file" name="file">과 Controller 파라미터 MultipartFile file은 이름(name)이 정확히 같아야 서로 연결됩니다. 이름이 다르면 값이 전달되지 않습니다.

왜 throws Exception 인가?

파일 저장 시 사용하는 transferTo()는 저장 도중 문제가 생길 수 있는(디스크 꽉 참, 권한 없음 등) 체크 예외(IOException)를 던집니다. 지금은 별도로 처리하지 않고 throws Exception으로 위(Spring)에 그대로 넘기고 있습니다.

UUID로 파일명 만들기

UUID uuid = UUID.randomUUID();
String fileName = uuid + "_" + file.getOriginalFilename();

초보자 관점

서로 다른 두 사람이 똑같이 "사진.jpg"라는 파일을 올리면, 이름이 겹쳐서 기존 파일을 덮어써버릴 수 있습니다.

Java 관점

UUID.randomUUID()는 사실상 절대 겹치지 않는 128비트짜리 무작위 값을 만들어줍니다. 이 값을 원본 파일명 앞에 붙여 "uuid_원본파일명" 형태의 새 이름을 만듭니다.

file.transferTo(saveFile)

File saveFile = new File(projectPath, fileName);
file.transferTo(saveFile);

Java 관점

File은 실제 파일이 아니라, 파일 시스템의 "경로"를 표현하는 객체입니다. transferTo()가 실행되는 순간 비로소 업로드된 데이터가 이 경로에 실제 파일로 저장됩니다.

객체지향 관점

파일을 "어디에 저장할지 결정하고 저장을 실행하는" 책임을 Controller가 아니라 Service가 맡고 있습니다. Controller는 요청을 받아 전달하는 역할만 하고, 저장 방식(경로 구성, 파일명 규칙)은 Service 안에 캡슐화되어 있습니다.

board.setFilename / board.setFilepath

board.setFilename(fileName);
board.setFilepath("/files/" + fileName);

실제 파일 내용은 디스크에, 그 파일을 다시 찾아올 수 있는 이름과 경로 문자열은 DB에 나눠서 저장하는 것입니다. 화면에서 다운로드 링크를 만들 때는 DB에 저장된 filepath를 그대로 사용합니다.

Step 4

왜 이렇게 작성했는가?

왜 파일 자체를 DB에 저장하지 않는가?

파일(특히 이미지)을 DB 컬럼에 바이너리로 직접 저장할 수도 있지만, DB 용량이 빠르게 커지고 조회 성능이 떨어집니다. 그래서 실무에서도 파일은 파일시스템/스토리지에, DB에는 경로만 저장하는 방식을 흔히 씁니다.

왜 UUID를 파일명 앞에 붙이는가?

사용자가 올리는 원본 파일명은 서로 겹칠 수 있습니다(예: 여러 명이 1.jpg를 올림). 겹친 이름으로 저장하면 먼저 저장된 파일이 덮어써져 사라집니다. UUID를 붙이면 저장 파일명이 항상 고유해집니다.

왜 Controller가 아니라 Service에서 파일을 저장하는가?

Controller는 "요청이 왔다, 무엇을 해야 하는지 전달한다"까지만 담당해야 합니다. 파일을 어떤 폴더 구조로, 어떤 이름 규칙으로 저장할지는 비즈니스 규칙이므로 Service에 있어야, 나중에 저장 방식이 바뀌어도(예: 로컬 디스크 → 클라우드 스토리지) Controller 코드는 건드리지 않아도 됩니다.

실행 흐름

파일 저장(파일 시스템)과 게시글 저장(DB)이 같은 메서드 안에서 순서대로 일어나는 것이 이번 commit에서 새로 추가된 흐름입니다.

Step 6

이전 Commit과 비교

이전 Commit — 텍스트만 작성

POST /board/writepro
  Board(title, content)
    ↓
  Service.boardWrite(board)
    ↓
  Repository.save()

현재 Commit — 파일 첨부 가능

POST /board/writepro (multipart)
  Board(title, content) + MultipartFile
    ↓
  Service.boardWrite(board, file)
    → 파일을 static/files 에 저장
    → board.filename / filepath 세팅
    ↓
  Repository.save()

이전에는 boardWrite(Board board) 하나만 받았지만, 이번 commit부터는 boardWrite(Board board, MultipartFile file)로 파라미터가 늘어나면서 게시글 작성과 수정 두 곳 모두에서 파일 처리가 가능해졌습니다.

Step 7

초보자가 하기 쉬운 착각

input type="file"만 추가하면 파일이 자동으로 업로드된다?

아닙니다. <form>의 enctype을 multipart/form-data로 바꿔주지 않으면, 브라우저는 파일 필드를 아예 전송하지 않거나 빈 값으로 보냅니다. 두 가지를 항상 같이 챙겨야 합니다.

파일이 DB에 저장되는 것 아닌가?

이번 코드에서 DB(board 테이블)에는 filename, filepath 문자열만 들어갑니다. 실제 이미지 파일은 서버의 static/files 폴더(파일시스템)에 저장됩니다.

MultipartFile 파라미터 이름은 아무거나 써도 된다?

아닙니다. HTML의 <input type="file" name="file">과 Controller의 MultipartFile file은 이름이 정확히 일치해야 값이 연결됩니다. name="upload"로 바꾸면 파라미터도 MultipartFile upload로 바꿔야 합니다.

파일을 첨부하지 않고 글을 쓰면 어떻게 될까?

지금 코드는 file이 비어 있어도 file.getOriginalFilename(), file.transferTo(...)를 그대로 실행합니다. 실제로 파일 없이 제출하면 예외가 발생하거나(구현에 따라) 빈 파일이 저장될 수 있습니다. 이 부분은 "파일이 있을 때만 저장"하도록 조건 처리가 필요한 지점입니다.

오늘 배운 것

  • 파일을 전송하려면 폼의 enctype을 multipart/form-data로 바꿔야 한다.
  • Spring은 MultipartFile 파라미터로 업로드된 파일을 자동으로 받아준다.
  • HTML input의 name과 Controller 파라미터 이름이 정확히 일치해야 값이 연결된다.
  • UUID를 파일명 앞에 붙이면 파일명 중복(덮어쓰기)을 막을 수 있다.
  • 파일 실제 데이터는 파일시스템에, 파일 경로 문자열만 DB에 저장하는 것이 일반적인 방식이다.
  • 파일 저장 로직은 Controller가 아니라 Service에 두어 역할을 분리한다.
Step 10

이해도 확인 질문

드래그해서 정답을 확인하세요.

  1. 파일 업로드 폼에서 enctype="multipart/form-data"를 빼먹으면 어떤 문제가 생기나요?

    브라우저가 파일 데이터를 서버로 제대로 전송하지 못합니다. 텍스트 필드만 전송되고, MultipartFile 파라미터는 빈 값이거나 null에 가까운 상태로 들어오게 됩니다.

  2. HTML의 <input type="file" name="file">에서 name="file"이 중요한 이유는?

    Spring이 요청에 담긴 여러 Part 중 어떤 것을 Controller의 MultipartFile 파라미터에 넣을지, 이름을 기준으로 찾기 때문입니다. HTML의 name과 Controller 파라미터명이 같아야 값이 연결됩니다.

  3. 왜 원본 파일명을 그대로 쓰지 않고 UUID를 앞에 붙이나요?

    서로 다른 사용자가 같은 이름의 파일을 올리면 기존 파일을 덮어써서 잃어버릴 수 있습니다. UUID는 거의 겹치지 않는 고유한 값이라, 파일명이 항상 유일하게 유지됩니다.

  4. 업로드된 파일이 실제로 DB 어디에 저장되나요?

    파일 자체는 DB가 아니라 서버의 static/files 폴더(파일시스템)에 저장됩니다. DB의 board 테이블에는 그 파일을 가리키는 filename, filepath 문자열만 저장됩니다.

  5. 파일 저장 로직을 Controller가 아니라 Service에 둔 이유는?

    Controller는 HTTP 요청을 받아 처리를 위임하는 역할만 해야 합니다. "어디에 어떤 이름 규칙으로 저장할지"는 비즈니스 로직이므로 Service에 있어야, 나중에 저장 방식(로컬 디스크 → 클라우드 등)이 바뀌어도 Controller는 그대로 둘 수 있습니다.

실습: 파일이 없는 게시글엔 다운로드 버튼 숨기기

지금은 파일을 첨부하지 않고 쓴 글이어도 boardview.html에 다운로드 버튼이 항상 보입니다.

board.filepath가 없는(=null인) 게시글에서는 다운로드 버튼이 아예 보이지 않도록 만들어보세요.

예시:
파일 첨부한 글 → [수정] [다운로드] [삭제]
파일 없는 글   → [수정] [삭제]

힌트:

  • Thymeleaf에서 조건부로 태그를 렌더링할 때 th:if를 씁니다.
  • th:if="${board.filepath != null}"를 다운로드 <a> 태그에 추가해보세요.
