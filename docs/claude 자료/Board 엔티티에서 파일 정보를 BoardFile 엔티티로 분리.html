Step 1

이번 커밋 한눈에 보기

이전까지는 Board 엔티티 하나에 게시글 정보와 파일 정보가 모두 들어있었습니다.
이번 커밋에서는 파일 정보를 BoardFile이라는 별도 엔티티로 분리했습니다.

이렇게 분리하면 게시글 하나에 파일이 없을 수도 있고, 나중에 여러 개의 파일을 붙일 수도 있는 구조가 됩니다.
또한 User 엔티티의 필드명을 id → loginId, pw → loginPw로 바꿔 PK와 혼동을 없앴습니다.

Service에서는 boardWrite와 boardModify를 분리하고, @Transactional을 올바르게 적용했습니다.
Repository에서는 Optional을 도입해 파일이 없는 경우를 안전하게 처리했습니다.

Step 2

무엇이 변경되었는가

BoardFile.java — 파일 정보 전용 엔티티

기존에 Board에 있던 filename, originalFilename, filepath 필드를 별도 엔티티로 분리했습니다.
@ManyToOne으로 Board를 참조해서 어느 게시글의 파일인지 연결합니다.

User.java — 필드명 변경

id → loginId, pw → loginPw로 변경했습니다.
JPA에서 id는 PK를 의미하는 관례와 충돌하기 때문에 명확하게 구분한 것입니다.

BoardFileRepository.java — 커스텀 메서드 추가

findByBoard_BoardId, existsByBoard_BoardId, deleteByBoard_BoardId 세 가지 메서드를 추가했습니다.
반환 타입을 Optional<BoardFile>로 선언해 파일이 없을 때의 처리를 명시적으로 만들었습니다.

UserRepository.java — findByLoginId 추가

필드명이 loginId로 바뀌면서 조회 메서드도 findByLoginId로 선언했습니다.

BoardService.java — 작성/수정 분리 및 @Transactional 적용

기존 boardWrite 하나로 작성과 수정을 모두 처리하던 것을 boardWrite와 boardModify로 분리했습니다.
파일 저장 로직은 saveBoardFile로, 파일 삭제 로직은 boardFileDelete로 메서드를 뽑아냈습니다.
DB 삭제가 필요한 메서드에 @Transactional을 붙였습니다.

BoardController.java — boardFile을 Model에 추가

view, modify, download 등 파일 정보가 필요한 곳에서 boardService.boardFileGet()을 호출해 Model에 전달하도록 수정했습니다.

Step 3

핵심 코드 설명

th:each의 iterStat — 반복 상태 객체

boardlist.html

<tr th:each="board, num : ${list}">
    <td th:text="${list.totalElements - (nowPage - 1) * list.size - num.index}"></td>

th:each에서 쉼표 뒤에 변수를 하나 더 선언하면 Thymeleaf가 반복 상태 정보를 담아줍니다.

  • num.index — 0부터 시작하는 인덱스
  • num.count — 1부터 시작하는 순번
  • num.size — 전체 목록 개수
  • num.first / num.last — 첫/마지막 항목 여부

상태 객체는 하나만 선언할 수 있으며, 이름은 자유롭게 지정 가능합니다.
역순 번호는 list.totalElements - (nowPage - 1) * list.size - num.index로 계산합니다.
페이지네이션이 있을 때 전체 개수와 현재 페이지 위치를 함께 계산해야 2페이지에서도 이어지는 번호가 됩니다.

@ManyToOne — Board를 참조하는 BoardFile

BoardFile.java

@ManyToOne
@JoinColumn(name = "board_id")
private Board board;

"BoardFile 여러 개가 Board 하나에 속한다"는 관계를 표현합니다.
DB에는 board_id 컬럼(숫자)으로 저장되지만, Java 코드에서는 Board 객체로 접근합니다.
숫자 ID 대신 객체를 참조하는 것이 JPA 연관관계의 핵심입니다.

Optional<BoardFile> — 파일이 없을 수 있음을 타입으로 표현

BoardFileRepository.java

Optional<BoardFile> findByBoard_BoardId(Integer boardId);

반환 타입을 Optional로 선언하면, 호출하는 쪽에서 반드시 "없을 수 있다"는 가능성을 인지하고 처리해야 합니다.
그냥 BoardFile로 반환하면 null 가능성이 코드에서 보이지 않아 나중에 NullPointerException이 터질 수 있습니다.

BoardService.java

public BoardFile boardFileGet(Integer board_id) {
    return boardFileRepository.findByBoard_BoardId(board_id).orElse(null);
}

.orElse(null)은 Optional을 벗겨서 BoardFile 또는 null을 반환합니다.
이후 호출하는 쪽에서 null 체크를 해야 합니다.

existsByBoard_BoardId — 존재 여부만 확인

BoardFileRepository.java

boolean existsByBoard_BoardId(Integer boardId);

findBy는 객체를 가져오고, existsBy는 true/false만 반환합니다.
객체 내용이 필요 없고 존재 여부만 확인할 때는 existsBy가 더 효율적입니다.
DB 쿼리도 SELECT * 대신 SELECT COUNT(*)가 실행됩니다.

@Transactional — 삭제 작업에 필수

BoardService.java

@Transactional
public void boardFileDelete(Integer boardId) {
    if (boardFileRepository.existsByBoard_BoardId(boardId)) {
        boardFileRepository.deleteByBoard_BoardId(boardId);
    }
}

deleteByBoard_BoardId 같은 커스텀 삭제 메서드는 내부적으로 EntityManager.remove()를 호출합니다.
이 작업은 반드시 트랜잭션 안에서만 실행될 수 있습니다.
@Transactional이 없으면 TransactionRequiredException이 발생합니다.

⭐ 현업 포인트

deleteById는 Spring Data JPA가 기본 제공하는 메서드라 내부에 이미 @Transactional이 붙어 있습니다.
반면 deleteByBoard_BoardId처럼 직접 선언한 커스텀 삭제 메서드는 @Transactional이 없습니다.
커스텀 삭제 메서드를 쓸 때는 반드시 @Transactional을 명시해야 합니다.

save()의 INSERT / UPDATE 분기

BoardService.java

Board savedBoard = boardRepository.save(board);

JPA의 save()는 ID 유무를 보고 자동으로 분기합니다.

  • ID가 null이면 → INSERT (새 레코드 생성)
  • ID가 있으면 → UPDATE (기존 레코드 수정)

수정 기능에서 boardView(id)로 가져온 객체는 이미 ID가 있으므로 save() 시 UPDATE가 됩니다.
save()의 반환값(savedBoard)을 써야 하는 이유는, 새 게시글은 저장 후에야 DB가 ID를 생성해 돌려주기 때문입니다.

JpaRepository 기본 제공 메서드 vs 커스텀 메서드

findById는 별도 선언 없이 바로 쓸 수 있습니다. JpaRepository가 기본으로 제공하기 때문입니다.

JpaRepository 기본 제공

findById(ID id)      // PK로 조회
findAll()            // 전체 조회
save(S entity)       // 저장/수정
deleteById(ID id)    // PK로 삭제
existsById(ID id)    // PK 존재 여부

반면 findByBoard_BoardId처럼 특정 필드로 조회하는 메서드는 Repository 인터페이스에 직접 선언해야 합니다.
JPA가 메서드 이름을 읽고 자동으로 쿼리를 만들어줍니다.

Step 4

왜 이렇게 작성했는가?

왜 BoardFile boardFile은 폼과 매칭되지 않는가?

BoardController.java

public String boardWritePro(Board board, Model model, MultipartFile file)

Spring MVC는 파라미터로 객체가 오면 폼의 name 속성과 객체의 필드명을 자동으로 매핑합니다.
폼에 name="title"이 있으면 Board.title로 매핑됩니다.

BoardFile의 필드는 fileId, board, originalFilename, filename, filepath인데,
폼에 이 이름들과 일치하는 input이 없습니다.
따라서 BoardFile은 폼에서 채워지는 게 아니라 Service에서 직접 값을 채워 넣습니다.

왜 DB의 PK를 board_id로 쓰는가?

현업에서는 두 가지 스타일이 혼재합니다.

스타일 1 — id로 통일

users → id (PK)
boards → id (PK)

Rails, Django 기본값
짧고 간결

스타일 2 — 접두사 붙이기

users → user_id (PK)
boards → board_id (PK)

Java/Spring 진영에서 많이 사용
조인 시 컬럼명이 명확

정답은 없고, 한 프로젝트 안에서 일관성이 중요합니다.
이 프로젝트는 board_id, user_id, file_id 방식으로 통일되어 있습니다.
단, 로그인 아이디처럼 PK가 아닌 필드에 id라는 이름을 쓰면 PK와 혼동되므로 loginId처럼 구체적으로 쓰는 게 좋습니다.

왜 deleteById는 없을 때 예외가 나고, deleteByXxx는 안 나는가?

사용 예시

// deleteById — 없으면 EmptyResultDataAccessException
boardRepository.deleteById(id);

// deleteByBoard_BoardId — 없으면 0건 삭제로 조용히 끝남
boardFileRepository.deleteByBoard_BoardId(boardId);

deleteById는 Spring Data JPA가 내부적으로 먼저 조회 후 삭제합니다. 조회 결과가 없으면 예외를 던집니다.
deleteByBoard_BoardId는 DELETE FROM ... WHERE board_id = ? 쿼리를 바로 실행하므로 0건 삭제로 끝납니다.
따라서 existsBy로 먼저 확인하거나 orElseThrow로 방어하는 게 안전합니다.

왜 Board에서 파일 정보를 분리했는가?

BoardFile.java

@Entity
@Table(name = "file")
@Data
public class BoardFile {
    @ManyToOne
    @JoinColumn(name = "board_id")
    private Board board;

    private String originalFilename;
    private String filename;
    private String filepath;
}

Board 하나에 파일이 없을 수도 있고, 나중에 여러 개가 붙을 수도 있습니다.
만약 Board 안에 파일 정보가 있다면, 파일이 없는 게시글도 null 컬럼을 갖게 됩니다.
별도 테이블로 분리하면 파일이 있을 때만 row가 생기므로 DB 설계가 깔끔해집니다.

왜 boardId(숫자)가 아닌 Board 객체를 넣어야 하는가?

BoardService.java

BoardFile boardFile = new BoardFile();
boardFile.setBoard(savedBoard);  // Board 객체 전체를 넣음

JPA는 객체 간의 관계를 숫자 ID가 아닌 객체 참조로 표현합니다.
@ManyToOne으로 선언된 필드의 타입이 Integer가 아니라 Board이기 때문입니다.
DB에 저장될 때 JPA가 자동으로 board_id 컬럼에 숫자를 넣어줍니다.

💡 개선 포인트

boardFileDelete에서 existsBy로 먼저 확인한 후 deleteBy를 호출하고 있습니다.
사실 파일이 없으면 deleteBy는 그냥 0건 삭제로 끝납니다. 오류가 나지 않습니다.
따라서 existsBy 체크 없이 바로 deleteBy만 호출해도 동작합니다. DB 쿼리를 한 번 줄일 수 있습니다.

왜 User.id를 loginId로 바꿨는가?

User.java

private String loginId;
private String loginPw;

JPA에서 id는 PK(@Id)를 의미하는 관례입니다.
필드명이 id이면 PK인지 로그인 아이디인지 코드만 봐서는 구분하기 어렵습니다.
또한 Repository에서 findById는 PK 조회 메서드로 예약되어 있어서, 로그인 ID로 조회하는 메서드 이름이 겹칩니다.

왜 boardWrite와 boardModify를 분리했는가?

이전 — 하나로 처리

boardWrite()
→ 작성도 처리
→ 수정도 처리
→ 파일 교체도 처리

현재 — 역할 분리

boardWrite() → 작성 전용
boardModify() → 수정 전용
saveBoardFile() → 파일 저장
boardFileDelete() → 파일 삭제

작성과 수정은 처리 방식이 다릅니다. 수정은 기존 파일을 먼저 삭제하는 과정이 필요합니다.
하나의 메서드로 두 가지를 처리하면 조건 분기가 복잡해지고, 유지보수가 어려워집니다.

왜 Optional을 쓰는가?

BoardFileRepository.java

Optional<BoardFile> findByBoard_BoardId(Integer boardId);

파일이 없는 게시글도 있기 때문에 조회 결과가 없을 수 있습니다.
반환 타입이 BoardFile이면 null 가능성이 타입에서 보이지 않아 호출하는 쪽에서 null 체크를 빠뜨리기 쉽습니다.
Optional<BoardFile>로 선언하면 컴파일 단계에서 "이 값은 없을 수 있다"는 것을 명시적으로 알 수 있습니다.

Optional의 주요 사용 패턴:

사용 예시

// 없으면 null 반환
BoardFile boardFile = repo.findByBoard_BoardId(id).orElse(null);

// 없으면 빈 객체 반환
BoardFile boardFile = repo.findByBoard_BoardId(id).orElse(new BoardFile());

// 없으면 예외 던짐 (반드시 있어야 하는 경우)
BoardFile boardFile = repo.findByBoard_BoardId(id)
    .orElseThrow(() -> new IllegalArgumentException("파일이 없습니다."));

Step 6

이전 커밋과 연결

이전 — Board 엔티티

Board
├── boardId (PK)
├── title
├── content
├── filename
├── originalFilename
└── filepath

현재 — 엔티티 분리

Board
├── boardId (PK)
├── title
└── content

BoardFile
├── fileId (PK)
├── board (→ Board)
├── filename
├── originalFilename
└── filepath

이전까지는 파일 정보가 Board 테이블의 컬럼으로 관리되었습니다.
파일이 없는 게시글도 filename, filepath 컬럼에 null 값을 갖고 있었습니다.

이번 커밋으로 파일 정보가 별도 테이블(file)로 분리되었습니다.
파일이 있는 게시글만 file 테이블에 row가 생기고, 없는 게시글은 row 자체가 없습니다.

Step 7

초보자가 하기 쉬운 착각

⚠ findById는 로그인 ID로 찾는 게 아니다

findById는 JpaRepository가 PK로 조회하는 기본 제공 메서드입니다.
로그인 ID(loginId 필드)로 찾으려면 findByLoginId를 Repository에 직접 선언해야 합니다.

⚠ Optional.isEmpty()가 null 체크는 아니다

file.isEmpty()는 MultipartFile의 내용이 비었는지 확인하는 것입니다.
file 자체가 null이면 isEmpty() 호출 시 NullPointerException이 발생합니다.
null 가능성이 있으면 file != null && !file.isEmpty()로 null 체크를 먼저 해야 합니다.

⚠ BoardFile에는 boardId 숫자가 아닌 Board 객체를 넣어야 한다

boardFile.setBoard(savedBoard)처럼 Board 객체 전체를 넣어야 합니다.
boardFile.setBoardId(1) 같은 방식은 @ManyToOne 구조에서 동작하지 않습니다.

⚠ save() 반환값을 써야 하는 경우가 있다

새 게시글 작성 시 boardRepository.save(board)를 호출하면 DB가 ID를 생성합니다.
원본 board 객체가 아니라 반환된 savedBoard에 ID가 채워집니다.
boardFile.setBoard(board)가 아닌 boardFile.setBoard(savedBoard)를 써야 올바른 ID가 연결됩니다.

⚠ deleteByBoard_BoardId는 @Transactional 없이 안 된다

deleteById는 기본 제공이라 내부에 이미 @Transactional이 있습니다.
직접 선언한 deleteByBoard_BoardId는 그렇지 않습니다. 반드시 호출하는 Service 메서드에 @Transactional을 붙여야 합니다.

오늘 배운 것

  • 엔티티를 분리하면 DB 설계가 유연해지고 null 컬럼이 줄어든다.
  • @ManyToOne은 숫자 ID가 아닌 Board 객체를 참조한다. DB에는 board_id 숫자로 저장된다.
  • Optional은 "없을 수 있다"를 타입으로 표현해 null 처리를 강제한다.
  • 커스텀 삭제 메서드(deleteByXxx)는 @Transactional 없이 실행할 수 없다.
  • save()는 ID가 null이면 INSERT, ID가 있으면 UPDATE를 실행한다.
  • save()의 반환값에 DB가 생성한 ID가 채워지므로 반환값을 써야 한다.
  • JpaRepository 기본 메서드(findById, deleteById 등)는 선언 없이 바로 사용 가능하다.
Step 10

이해도 확인 질문

  1. BoardFile에서 @ManyToOne으로 Board 객체를 참조하는데, DB에는 어떻게 저장되는가?

    DB에는 board_id 컬럼에 숫자(PK 값)로 저장됩니다. Java 코드에서는 객체 참조로 표현하지만, JPA가 저장 시 자동으로 숫자로 변환합니다.

  2. findById는 별도 선언 없이 쓸 수 있는데, findByLoginId는 선언해야 하는 이유는?

    findById는 JpaRepository가 기본으로 제공하는 메서드입니다. findByLoginId는 직접 선언해야 JPA가 인식하고 메서드 이름을 분석해 쿼리를 자동 생성합니다.

  3. deleteByBoard_BoardId를 호출할 때 @Transactional이 없으면 어떻게 되는가?

    TransactionRequiredException이 발생합니다. 커스텀 삭제 메서드는 내부적으로 EntityManager.remove()를 호출하는데, 이 작업은 반드시 트랜잭션 안에서만 실행될 수 있기 때문입니다.

  4. 새 게시글 작성 시 boardRepository.save(board)에서 원본 board 대신 반환값 savedBoard를 써야 하는 이유는?

    새 게시글은 저장 후에야 DB가 ID를 생성합니다. 반환된 savedBoard에 이 ID가 채워지고, 원본 board에는 ID가 없습니다. boardFile.setBoard(board)를 쓰면 ID 없는 객체가 연결되어 오류가 발생할 수 있습니다.

  5. Optional.orElse(null)과 Optional.orElseThrow()는 각각 언제 쓰는가?

    값이 없어도 되는 경우(파일 등 선택 정보)에는 orElse(null)을 쓰고 이후 null 체크를 합니다. 값이 반드시 있어야 하는 경우(게시글 조회 등)에는 orElseThrow()로 없으면 예외를 던집니다.
