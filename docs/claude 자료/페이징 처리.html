Step 1

이번 Commit 한눈에 보기

이번 두 커밋에서는 게시글 목록 페이지에 페이징 기능을 추가했습니다.
게시글이 수백 개라도 한 페이지에 10개씩만 보여주고, 아래에 1 2 3 ... 페이지 번호 버튼이 나타나게 만드는 기능입니다.

커밋 1 (e7777f1): List<Board>를 Page<Board>로 바꾸고, Controller에 Pageable 파라미터를 추가했습니다.
커밋 2 (81521c6): 현재 페이지, 시작 페이지, 끝 페이지를 계산해 Model에 담고, HTML에 페이지 번호 버튼을 렌더링했습니다.

Spring Data JPA가 페이징 처리를 거의 자동으로 해줍니다. 개발자가 직접 SQL에 LIMIT, OFFSET을 쓰지 않아도 됩니다.

Step 2

무엇이 변경되었는가

BoardService.java 커밋 1

// 이전
public List<Board> boardList(){
    return boardRepository.findAll();
}

// 현재
public Page<Board> boardList(Pageable pageable){
    return boardRepository.findAll(pageable);
}
  • 왜 변경? 전체 목록 대신 한 페이지 분량의 게시글만 가져오기 위해
  • 역할: Pageable 조건(몇 페이지, 몇 개씩, 정렬)을 Repository에 그대로 전달
  • 반환 타입 변화: List → Page — Page는 게시글 목록뿐 아니라 전체 페이지 수, 현재 페이지 번호 등 메타정보도 포함

BoardController.java — Pageable 파라미터 추가 커밋 1

@GetMapping("board/list")
public String boardlist(Model model,
                        @PageableDefault(page=0, size=10, sort="id", direction = Sort.Direction.DESC) Pageable pageable){
    model.addAttribute("list", boardService.boardList(pageable));
    return "boardlist";
}
  • 왜 추가? Spring이 HTTP 요청의 쿼리 파라미터를 Pageable 객체로 자동 변환해 넘겨줌
  • @PageableDefault: URL에 페이지 정보가 없을 때 사용할 기본값 설정

BoardController.java — 페이지 범위 계산 추가 커밋 2

Page<Board> list = boardService.boardList(pageable);

int nowPage = list.getPageable().getPageNumber() + 1;
int startPage = Math.max(nowPage - 4, 1);
int endPage = Math.min(nowPage + 5, list.getTotalPages());

model.addAttribute("list", list);
model.addAttribute("nowPage", nowPage);
model.addAttribute("startPage", startPage);
model.addAttribute("endPage", endPage);
  • 왜 추가? HTML에서 "1 2 3 4 5" 같은 페이지 버튼을 만들려면 어디서 어디까지 버튼을 그려야 하는지 알아야 함
  • 계산한 3개의 값을 Model에 담아 Thymeleaf에 전달

boardlist.html — 페이지 버튼 추가 커밋 2

<th:block th:each="page: ${#numbers.sequence(startPage, endPage)}">
    <a th:if="${page != nowPage}" th:href="@{/board/list(page=${page-1})}" th:text="${page}"></a>
    <strong th:if="${page == nowPage}" th:text="${page}" style="color:red"></strong>
</th:block>
  • 왜 추가? 사용자가 클릭해서 다른 페이지로 이동할 수 있는 버튼을 화면에 표시하기 위해
  • 현재 페이지는 <strong>으로 빨간색 강조, 나머지는 링크(<a>)로 표시
Step 3

핵심 코드 설명

Pageable과 @PageableDefault

@PageableDefault(page=0, size=10, sort="id", direction = Sort.Direction.DESC) Pageable pageable

초보자 관점

"몇 페이지를, 몇 개씩, 어떤 순서로 가져올지"를 담은 설정 객체라고 생각하면 됩니다.
마치 도서관에서 "최신 책 기준으로 10권씩, 지금은 1번째 묶음 주세요"라고 요청하는 것과 같습니다.

Spring 관점

브라우저에서 /board/list?page=2로 요청하면, Spring이 URL의 page=2를 읽어서 자동으로 Pageable 객체를 만들어 메서드에 넣어줍니다.
URL에 page 파라미터가 없으면 @PageableDefault에 설정한 기본값(page=0)을 사용합니다.

@PageableDefault(
    page = 0,          // 기본 페이지: 0번째 (첫 페이지, 0-based)
    size = 10,         // 한 페이지에 게시글 10개
    sort = "id",       // id 컬럼 기준 정렬
    direction = Sort.Direction.DESC  // 내림차순 (최신 글이 위)
)

Page<T>와 List<T>의 차이

List와 Page 모두 Board 객체 안에 담긴 id, title, content 등 데이터는 완전히 동일합니다.
정렬 순서가 다르게 보이는 이유는 @PageableDefault에 sort=id DESC를 설정했기 때문입니다.
구조의 차이는 단 하나입니다. List는 데이터만 / Page는 데이터 + 메타정보.

Page는 단순 리스트가 아닙니다.
게시글 목록뿐 아니라 "전체 몇 페이지인지", "지금 몇 번째 페이지인지", "마지막 페이지인지" 같은 정보를 함께 가지고 있습니다.
페이지 버튼을 만들려면 이 메타정보가 꼭 필요하기 때문에 List에서 Page로 바꾼 것입니다.

Page도 순회(반복)가 가능한 이유

Thymeleaf에서 th:each="board: ${list}"로 Page를 바로 순회할 수 있습니다.
Page가 Iterable 인터페이스를 구현하기 때문입니다.
내부적으로는 getContent()를 호출해 List<Board>를 꺼낸 뒤 반복합니다.

// Page 인터페이스 계층 구조
Page<T>
 └── Slice<T>
      └── Iterable<T>   ← th:each로 바로 순회 가능한 이유

// Page 안에서 게시글 목록만 꺼내고 싶다면
List<Board> boardList = list.getContent();

Page가 인터페이스인데 누가 구현하나?

Page는 인터페이스이므로 getTotalPages() 같은 메서드를 직접 구현해야 할 것 같지만, 그럴 필요가 없습니다.
Spring Data JPA가 런타임에 자동으로 구현체를 만들어 줍니다.

// 개발자가 선언한 것 (인터페이스)
Page<Board>
BoardRepository extends JpaRepository<Board, Integer>

// Spring이 앱 시작 시 자동으로 만드는 것 (구현체)
Page      →  PageImpl<Board>        (getTotalPages 등 모두 구현됨)
Repository →  SimpleJpaRepository   (save, findAll 등 모두 구현됨)

BoardRepository에 아무것도 선언하지 않아도 save(), findAll(), findById(), deleteById()가 동작하는 이유도 같습니다.
Spring이 JpaRepository를 상속한 인터페이스를 발견하면, 앱 시작 시 SimpleJpaRepository 기반의 구현체를 자동 생성해 주입합니다.
이를 Spring Data JPA Repository 추상화라고 합니다.

findAll()에 Pageable 말고 다른 인자도 들어갈 수 있나?

JpaRepository가 기본으로 제공하는 findAll 변형은 세 가지입니다.

findAll()                  // 전체, 정렬 없음   → List<Board>
findAll(Sort sort)         // 전체, 정렬만      → List<Board>
findAll(Pageable pageable) // 전체, 페이징+정렬 → Page<Board>

세 가지 모두 WHERE 조건이 없습니다. 전부 가져오되 방식만 다릅니다.
"조건(WHERE) + 페이징"을 같이 하려면 Repository에 메서드를 직접 선언해야 합니다.

// BoardRepository에 선언 추가 — 메서드 이름으로 쿼리 자동 생성
Page<Board> findByTitleContaining(String keyword, Pageable pageable);
// → SELECT * FROM board WHERE title LIKE '%keyword%' LIMIT 10 OFFSET 0

이것이 다음 커밋에서 배울 검색 + 페이징 연동입니다.
Pageable은 "어떻게 잘라서 가져올지"만 담당하고, "무엇을 가져올지(WHERE)"는 메서드 이름이나 @Query가 담당합니다.

nowPage / startPage / endPage 계산

int nowPage = list.getPageable().getPageNumber() + 1;
int startPage = Math.max(nowPage - 4, 1);
int endPage = Math.min(nowPage + 5, list.getTotalPages());

왜 +1을 하나?

Spring의 페이지 번호는 0부터 시작합니다 (0-based index).
하지만 사용자에게 보여줄 때는 1부터 시작해야 자연스럽습니다.
그래서 getPageNumber()가 반환한 0-based 번호에 +1을 해서 화면용 번호로 변환합니다.

startPage와 endPage

현재 페이지가 7이면, 3~12 범위의 버튼을 표시하는 것이 자연스럽습니다 (앞으로 4개, 뒤로 5개).
하지만 1페이지 근처에서는 startPage가 0이나 -1이 될 수 있고, 마지막 페이지 근처에서는 endPage가 총 페이지 수를 넘을 수 있습니다.

Math.max(nowPage - 4, 1) → startPage가 최소 1 이하로 내려가지 않도록
Math.min(nowPage + 5, list.getTotalPages()) → endPage가 총 페이지 수를 넘지 않도록

#numbers.sequence()와 th:block

<th:block th:each="page: ${#numbers.sequence(startPage, endPage)}">

#numbers.sequence(start, end)

Thymeleaf가 제공하는 유틸리티 함수입니다.
#numbers.sequence(3, 7)이면 [3, 4, 5, 6, 7] 숫자 배열을 만들어줍니다.
th:each와 함께 쓰면 startPage부터 endPage까지 반복하며 버튼을 생성합니다.

th:block

Thymeleaf 전용 태그입니다. <div>나 <span>과 달리 실제 HTML에는 아무 흔적도 남기지 않습니다.
페이지 버튼들 사이에 불필요한 래퍼 태그 없이 반복 처리만 하고 싶을 때 사용합니다.

th:block 사용 시 — 출력 HTML

<a href="?page=2">3</a>
<a href="?page=3">4</a>
<strong>5</strong>
<a href="?page=5">6</a>

div 사용 시 — 불필요한 태그 포함

<div><a href="?page=2">3</a></div>
<div><a href="?page=3">4</a></div>
<div><strong>5</strong></div>
<div><a href="?page=5">6</a></div>
Step 4

왜 이렇게 작성했는가?

왜 List에서 Page로 바꿨나?

게시글 목록에 페이징 버튼을 만들려면 "총 몇 페이지인지"를 알아야 합니다.
List에는 데이터만 있고 "전체 페이지 수"를 구할 방법이 없습니다.
Page는 list.getTotalPages(), list.getPageable().getPageNumber() 같은 메서드를 제공하기 때문에 페이지 버튼 계산이 가능합니다.

왜 @PageableDefault를 사용하나?

사용자가 처음 /board/list로 접속할 때는 URL에 ?page=0 같은 정보가 없습니다.
이때 @PageableDefault에 설정한 기본값이 적용됩니다.
"기본적으로 첫 번째 페이지(0)에서 10개씩, id 내림차순으로 보여줘"라는 설정입니다.

왜 페이지 계산 로직을 View가 아닌 Controller에 두나?

페이지 범위 계산(Math.max, Math.min)은 데이터 처리 로직입니다.
Thymeleaf(View)는 화면 표시에만 집중해야 하고, 계산은 Controller나 Service가 담당하는 것이 올바른 역할 분리입니다.
계산 결과를 Model에 담아서 View에 넘기면, View는 그냥 숫자를 받아서 반복만 하면 됩니다.

왜 페이지 링크 URL은 page-1을 전달하나?

th:href="@{/board/list(page=${page-1})}"

화면에 보이는 페이지 번호는 1-based (1, 2, 3...)이지만, Spring은 0-based (0, 1, 2...)를 기대합니다.
"3번 페이지" 버튼을 클릭하면 ?page=2로 요청해야 Spring이 올바르게 3번째 페이지를 꺼내옵니다.

100개 중 10개를 걸러서 보여주는 건가? 아니면 처음부터 10개만 가져오나?

처음부터 10개만 가져옵니다. 100개를 로드한 뒤 나머지를 버리는 게 아닙니다.
findAll(pageable)을 호출하면 JPA가 SQL을 두 번 실행합니다.

// 쿼리 1: 해당 페이지 데이터만 (page=2, size=10 기준)
SELECT * FROM board ORDER BY id DESC LIMIT 10 OFFSET 20

// 쿼리 2: 전체 개수 — getTotalPages() 계산에 필요
SELECT COUNT(*) FROM board

DB에서 실제로 10개만 전송하므로 게시글이 100만 개여도 조회 성능은 동일합니다.
OFFSET = 페이지 번호 × size 공식으로 몇 번째 행부터 가져올지를 결정합니다.

page=0 (첫 페이지)

SELECT * FROM board
ORDER BY id DESC
LIMIT 10 OFFSET 0

page=2 (3번째 페이지)

SELECT * FROM board
ORDER BY id DESC
LIMIT 10 OFFSET 20

Step 6

이전 Commit과 비교

이전 — 전체 목록 조회

GET /board/list
  ↓
boardList()
  ↓
findAll()
  ↓
List<Board> (전체)
  ↓
Model에 list만 담음
  ↓
HTML: 게시글만 나열

현재 — 페이징 조회

GET /board/list?page=2
  ↓
boardList(pageable)
  ↓
findAll(pageable)
  ↓
Page<Board> (10개 + 메타정보)
  ↓
nowPage/startPage/endPage 계산
  ↓
HTML: 게시글 + 페이지 버튼

코드 변경량은 적지만 사용자 경험이 크게 달라집니다.
게시글이 1000개 있어도 한 페이지에 10개만 로드하므로 성능도 크게 개선됩니다.

Step 7

초보자가 하기 쉬운 착각

Page가 List를 상속한 것 아닌가?

Page는 List를 상속하지 않습니다.
Page는 Spring Data에서 제공하는 별도의 인터페이스입니다.
page.getContent()를 호출하면 List<Board>를 꺼낼 수 있습니다.
Thymeleaf에서 th:each="board: ${list}"로 Page를 직접 순회할 수 있는 이유는 Page가 Iterable을 구현하기 때문입니다.

nowPage에 +1을 빼먹으면?

화면에 페이지 번호가 1 대신 0, 2 대신 1로 표시됩니다.
더 심각하게는 startPage 계산에서 Math.max(0 - 4, 1) = 1이 되어 첫 페이지에서는 우연히 맞지만, 2번째 페이지에서는 startPage가 잘못 계산됩니다.
+1은 반드시 필요합니다.

#numbers.sequence()에서 # 을 빼면?

${numbers.sequence(...)}처럼 #을 빼면, Thymeleaf는 모델에서 numbers라는 이름의 변수를 찾습니다.
그런 변수가 없으므로 null이 되어 페이지 버튼이 아무것도 렌더링되지 않습니다.
Thymeleaf 유틸리티 객체(#numbers, #strings, #lists 등)는 반드시 #를 붙여야 합니다.

페이지 링크 URL에서 page-1이 헷갈린다

화면 버튼: 1, 2, 3, 4, 5 (1-based)
Spring이 받는 값: 0, 1, 2, 3, 4 (0-based)

"3" 버튼을 클릭하면 ?page=2를 전송해야 합니다. 그래서 page=${page-1}입니다.
화면 번호 − 1 = Spring이 기대하는 번호라고 기억하면 됩니다.

사용자가 URL에 ?page=9999를 직접 입력해서 조작하면?

가능합니다. Spring은 존재하지 않는 페이지 번호를 요청받으면 예외 없이 빈 Page를 반환합니다.
게시글 0개짜리 빈 화면이 보일 뿐, 오류는 나지 않습니다.

막고 싶다면 Controller에서 직접 검증하면 됩니다.

Page<Board> list = boardService.boardList(pageable);
if (pageable.getPageNumber() >= list.getTotalPages()) {
    return "redirect:/board/list"; // 첫 페이지로 리다이렉트
}

단, 이 게시판처럼 공개된 목록 조회는 굳이 막지 않아도 됩니다.
막는 게 중요한 경우는 인증이 필요한 데이터에 page 파라미터로 접근할 수 있을 때입니다.

Step 9

오늘 배운 것

  • Pageable은 "몇 페이지, 몇 개씩, 어떤 정렬"을 담은 객체로, Spring이 URL 파라미터를 읽어 자동 생성한다.
  • @PageableDefault로 URL에 파라미터가 없을 때 사용할 기본값을 설정할 수 있다.
  • Page<T>는 List<T>에 총 페이지 수, 현재 페이지 번호 등 페이징 메타정보가 추가된 타입이다.
  • Spring의 페이지 번호는 0-based이므로, 화면에 표시할 때는 +1을 해야 한다.
  • Math.max/min으로 startPage/endPage가 1 이하나 총 페이지 수 초과로 벗어나는 것을 막는다.
  • Thymeleaf의 #numbers.sequence(start, end)는 숫자 범위 배열을 만들어 페이지 버튼 반복에 활용한다.
  • th:block은 Thymeleaf 제어 전용 태그로 실제 HTML에는 아무 태그도 남기지 않는다.
Step 10

이해도 확인 질문

  1. Page<Board>와 List<Board>의 차이는 무엇인가요?

    List는 데이터만 담습니다. Page는 데이터(게시글 목록) 외에도 총 페이지 수, 현재 페이지 번호, 전체 데이터 개수 등의 메타정보를 함께 포함합니다. 페이지 버튼을 만들려면 이 메타정보가 필요하기 때문에 List 대신 Page를 사용합니다.

  2. nowPage = list.getPageable().getPageNumber() + 1에서 왜 +1을 하나요?

    Spring Data JPA의 페이지 번호는 0부터 시작합니다(0-based). 첫 번째 페이지가 0, 두 번째가 1입니다. 하지만 사용자에게는 1번 페이지, 2번 페이지로 보여줘야 하므로 +1을 해서 1-based 번호로 변환합니다.

  3. startPage에 Math.max, endPage에 Math.min을 사용하는 이유는?

    현재 페이지가 2일 때 startPage = 2-4 = -2가 되어 음수가 될 수 있습니다. Math.max(-2, 1)로 최소값을 1로 보정합니다. 반대로 마지막 근처 페이지에서는 endPage가 총 페이지 수를 초과할 수 있습니다. Math.min으로 초과하지 않도록 제한합니다.

  4. #numbers.sequence(startPage, endPage)에서 #을 빼면 어떻게 되나요?

    Thymeleaf는 #numbers를 내장 유틸리티 객체로 인식합니다. #을 빼면 모델에서 numbers라는 변수를 찾는데, 그런 변수가 없으므로 null이 됩니다. 결과적으로 페이지 버튼이 아무것도 렌더링되지 않습니다.

  5. 페이지 링크 URL이 th:href="@{/board/list(page=${page-1})}"인 이유는?

    화면에 표시되는 페이지 번호는 1-based(1, 2, 3...)이지만, Spring Controller가 받는 page 파라미터는 0-based(0, 1, 2...)여야 합니다. "3" 버튼을 클릭할 때 ?page=2를 전송해야 Spring이 3번째 페이지를 조회합니다. 그래서 화면 번호에서 1을 빼서 전송합니다.

Step 11

작은 실습

실습: 페이지당 게시글 수를 5개로 바꿔보기

현재 한 페이지에 10개의 게시글이 나옵니다.
이것을 5개씩 보이도록 변경해보세요.

수정할 코드:

@PageableDefault(page=0, size=10, sort="id", direction = Sort.Direction.DESC) Pageable pageable

힌트:
size=10을 size=5로 바꾸면 됩니다.
변경 후 게시글 11개 이상 있을 때 /board/list에 접속해서 페이지 버튼이 더 많이 생기는지 확인해보세요.

추가 도전:
페이지 버튼 범위를 현재 "앞 4개, 뒤 5개"에서 "앞 2개, 뒤 2개"로 줄여보세요.
nowPage - 4와 nowPage + 5 값을 바꾸면 됩니다.
