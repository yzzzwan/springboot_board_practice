Step 1

이번 Commit 한눈에 보기

이번 커밋에서 게시글 삭제 기능을 완성했어. 상세 페이지에 삭제 버튼을 추가하고, 버튼 클릭 시 id를 URL로 전달해서 DB에서 해당 게시글을 삭제하는 흐름이야.

삭제 후에는 바로 목록 페이지로 이동해. 이때 단순히 뷰 이름을 반환하지 않고 redirect:를 사용해서 새 HTTP 요청으로 목록을 다시 불러오는 게 핵심이야.

추가로 기존 write() 메서드 이름을 boardWrite()로 정리하면서 네이밍 컨벤션도 맞췄어.

Step 3

핵심 코드 설명

BoardService — boardDelete()

public void boardDelete(Integer id){
    boardRepository.deleteById(id);
}

초보자 관점: "id를 받아서 그 번호의 게시글을 DB에서 지운다"

Java 관점: 반환 타입이 void. 삭제는 결과를 돌려줄 게 없으니까 반환값이 없어.

Spring/JPA 관점: deleteById()는 JpaRepository가 기본으로 제공하는 메서드야. 내가 직접 구현한 게 아님. 내부에서 DELETE FROM board WHERE id = ? SQL이 자동으로 실행돼.

BoardController — boardDelete()

@GetMapping("/board/delete")
public String boardDelete(Integer id){
    boardService.boardDelete(id);
    return "redirect:/board/list";
}

여기서 핵심은 두 가지야.

  • @GetMapping으로 삭제? — REST 원칙상 삭제는 HTTP DELETE 메서드를 써야 하는데, 브라우저 <a> 태그는 GET 요청만 보낼 수 있어. 지금은 편의상 GET으로 처리했어. 주석으로 남긴 @DeleteMapping이 바로 그 고민의 흔적이야.
  • redirect: — 삭제 후 뷰 이름이 아니라 URL 경로로 이동 지시. /board/list Controller를 다시 거쳐서 목록 데이터를 새로 조회해.

@DeleteMapping으로 구현했다면?

브라우저 <a> 태그는 GET만 보낼 수 있어서 두 가지 방법이 필요해.

방법 1 — HiddenHttpMethodFilter (JS 없이)

application.properties에 필터를 활성화하고, <form>에 히든 필드를 넣으면 Spring이 POST를 DELETE로 바꿔서 처리해줘.

// application.properties
spring.mvc.hiddenmethod.filter.enabled=true
<!-- boardview.html: a 태그 대신 form으로 교체 -->
<form th:action="@{/board/delete/{id}(id=${board.id})}" method="post">
  <input type="hidden" name="_method" value="DELETE">
  <button type="submit" class="btn-delete">삭제</button>
</form>
// Controller
@DeleteMapping("/board/delete/{id}")
public String boardDelete(@PathVariable Integer id){
    boardService.boardDelete(id);
    return "redirect:/board/list";
}

방법 2 — JavaScript fetch

<button class="btn-delete" onclick="deleteBoard([[${board.id}]])">삭제</button>

<script>
function deleteBoard(id) {
  fetch('/board/delete/' + id, { method: 'DELETE' })
    .then(() => location.href = '/board/list');
}
</script>
@DeleteMapping이면 GET으로 URL 직접 접근 시 405 에러가 난다 @DeleteMapping("/board/delete")로 등록된 URL에 브라우저가 GET /board/delete?id=3으로 요청하면 서버가 405 Method Not Allowed를 반환해. Spring은 URL뿐만 아니라 HTTP 메서드까지 함께 매핑하기 때문이야. 같은 URL이라도 GET/POST/DELETE는 서로 다른 Controller야.

boardview.html — Thymeleaf 삭제 링크

<button class="btn-delete">
  <a th:href="@{/board/delete(id=${board.id})}">삭제</a>
</button>

@{/board/delete(id=${board.id})}는 Thymeleaf가 /board/delete?id=3 형태의 URL로 변환해줘. 여기서 board.id는 Controller가 Model에 담아서 넘겨준 게시글 객체의 id야.

write() → boardWrite() 이름 변경

// 이전
public void write(Board board){ ... }

// 이번
public void boardWrite(Board board){ ... }

write()는 무엇을 쓰는지 모호해. boardWrite()처럼 도메인을 이름에 포함하면 나중에 코드를 읽을 때 훨씬 명확해.

Step 4

왜 이렇게 작성했는가?

왜 deleteById()를 Controller에서 직접 쓰지 않고 Service를 거치는가?

지금은 단순 삭제라서 Service가 한 줄짜리처럼 보여. 하지만 나중에 "삭제 전 권한 체크", "첨부 파일도 같이 삭제", "삭제 로그 기록" 같은 비즈니스 로직이 생기면 Controller는 손 안 대고 Service만 수정하면 돼. Controller는 HTTP 요청/응답 처리에만 집중하는 게 역할 분리의 핵심이야.

왜 return "redirect:/board/list"인가?

return "boardlist"와 return "redirect:/board/list"는 완전히 다르게 동작해.

return "boardlist" ❌

GET /board/delete?id=3
  ↓ 삭제 실행
boardlist.html 렌더링
← /board/list Controller를
    거치지 않음
Model에 list 데이터 없음
→ 빈 화면 or 에러

return "redirect:/board/list" ✅

GET /board/delete?id=3
  ↓ 삭제 실행
302 응답 → 브라우저에게
"이 URL로 다시 요청해"
GET /board/list (새 요청)
@GetMapping("board/list") 실행
→ list를 Model에 담음
PRG 패턴 (Post-Redirect-Get) 삭제는 데이터를 바꾸는 작업이야. 처리 완료 후 새 GET 요청으로 목록을 다시 불러와야 해. 그렇지 않으면 사용자가 새로고침했을 때 삭제 요청이 재실행될 수 있고, 브라우저가 "이 페이지를 다시 제출하시겠습니까?" 경고를 띄워.

왜 @GetMapping으로 삭제를 처리했는가?

HTML <a> 태그와 <form method="get">은 GET 요청만 보낼 수 있어. 삭제에 HTTP DELETE를 쓰려면 JavaScript(fetch/axios)나 히든 필드 방식이 필요한데, 지금 학습 단계에서는 GET으로 간단하게 처리한 거야.

Step 7

초보자가 하기 쉬운 착각

redirect: 뒤에 템플릿 파일 이름을 쓰면 안 돼 redirect:boardlist가 아니라 redirect:/board/list — URL 경로를 써야 해. 템플릿 이름을 쓰면 Controller를 거치지 않아서 모델 데이터가 없는 빈 화면이 뜨거나 에러가 날 수 있어.
@GetMapping으로 삭제하는 건 올바른 REST 방식이 아니야 지금은 브라우저 <a> 태그의 한계로 GET을 쓴 거야. 실제 서비스에서는 HTTP DELETE 메서드로 요청하는 게 맞아. 주석으로 남긴 @DeleteMapping이 그 고민의 흔적이야.
deleteById()에 없는 id를 넣으면 예외가 발생해 지금은 예외 처리가 없어서 존재하지 않는 id로 /board/delete?id=999에 접근하면 500 에러가 날 수 있어. 나중에 existsById()로 확인하거나 @ExceptionHandler로 처리하게 될 거야.
write() → boardWrite() 이름 변경은 기능 변경이 아니야 메서드 이름만 바꿨을 뿐, 동작은 똑같아. 하지만 Controller에서 호출 이름도 같이 바꿔야 에러가 안 나. 한 곳만 바꾸면 컴파일 에러가 발생해.

Step 9

오늘 배운 것

  • boardRepository.deleteById(id) — JPA가 기본 제공하는 삭제 메서드, SQL DELETE를 자동 실행
  • return "redirect:/board/list" — 처리 후 새 HTTP GET 요청으로 페이지 이동 (목록 데이터 재조회)
  • th:href="@{/path(param=${value})}" — Thymeleaf에서 URL 쿼리 파라미터 전달 방법
  • 삭제 후 redirect 없이 뷰 이름 반환하면 목록 데이터가 없어서 화면이 비거나 에러가 남
  • 브라우저 <a> 태그는 GET 요청만 보낼 수 있어서 지금은 @GetMapping으로 삭제를 처리했지만, REST 원칙상 DELETE 메서드가 올바름
  • 메서드 이름에 도메인을 포함하면 (boardWrite, boardDelete) 코드 가독성이 좋아짐
Step 10

이해도 확인 질문

  • 삭제 후 return "boardlist"를 반환하면 어떤 문제가 생기는가?

    /board/list Controller를 거치지 않아서 목록 데이터(model에 담긴 list)가 없어. 화면에 게시글 목록이 나오지 않거나 타임리프 th:each 처리 중 에러가 날 수 있어. redirect: 가 새 GET 요청을 만들어서 Controller → Service → Repository 순서로 데이터를 다시 가져오는 게 핵심이야.

  • th:href="@{/board/delete(id=${board.id})}"가 실제로 만드는 URL은?

    /board/delete?id=3 형태의 URL이 만들어져. id가 3인 게시글의 상세 페이지라면. Thymeleaf가 @{} 안의 (key=value) 형식을 쿼리 파라미터로 변환해줘.

  • 지금 방식(@GetMapping으로 삭제)의 단점은?

    REST 원칙상 삭제는 HTTP DELETE 메서드를 써야 해. GET으로 삭제하면 1) 검색 엔진 크롤러가 링크를 타고 게시글을 삭제할 수 있고, 2) 브라우저 히스토리에서 뒤로가기 등으로 재실행될 수 있어. 실제 서비스에서는 JS fetch로 DELETE 요청을 보내거나, Form + HiddenHttpMethodFilter를 써야 해.

  • 없는 id로 삭제를 시도하면 지금 코드에서 어떤 일이 일어나는가?

    JPA의 deleteById()는 존재하지 않는 id를 받으면 EmptyResultDataAccessException을 발생시켜. 현재 코드에는 예외 처리가 없어서 500 에러 페이지가 뜨게 돼. existsById()로 먼저 확인하거나 @ExceptionHandler로 처리해야 해.

  • PRG 패턴이 무엇이고 왜 쓰는가?

    Post-Redirect-Get의 약자야. 데이터를 변경하는 작업(삭제, 등록 등) 후에 바로 뷰를 렌더링하지 않고 redirect로 새 GET 요청을 발생시키는 패턴이야. 이렇게 하면 사용자가 새로고침해도 삭제/등록이 중복 실행되지 않고, 브라우저 "폼 재제출 경고"도 뜨지 않아.

Step 11

작은 실습

게시글 수정(Update) 메서드 뼈대 만들기

BoardService에 게시글 수정 메서드를 직접 구현해봐.

  • 메서드 이름: boardUpdate
  • 파라미터: Integer id, Board newBoard
  • boardView(id)로 기존 게시글을 먼저 꺼내야 해
  • boardRepository.save()를 사용 — JPA는 이미 id가 있는 엔티티를 save하면 UPDATE SQL이 실행됨

힌트: 기존 board 객체의 title, content를 newBoard에서 받은 값으로 바꾼 후 save()하면 돼.

Step 12

다음 Commit을 위한 준비

  • 게시글 수정 페이지 — 기존 내용을 폼에 미리 채워서 보여주고 저장하는 흐름. boardView()로 데이터를 꺼내서 폼에 바인딩해야 함
  • @PathVariable vs @RequestParam — URL 파라미터를 받는 두 가지 방식 차이. /board/view/1 (PathVariable) vs /board/view?id=1 (RequestParam)
  • Optional 안전하게 사용하기 — 지금 쓰는 .get()은 없는 id면 NoSuchElementException이 발생해. .orElseThrow()로 더 안전하게 처리 가능
  • HTTP 메서드 제대로 쓰기 — Form의 hidden 필드 + HiddenHttpMethodFilter로 DELETE 요청 보내는 방법, 또는 JavaScript fetch 활용
