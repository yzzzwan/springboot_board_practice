Step 1

이번 커밋 한눈에 보기

이번 커밋에서는 세 가지 문제를 해결했습니다.

첫째, http://localhost:8080/으로 접속했을 때 Whitelabel Error가 뜨던 문제를 고쳤습니다.
초기 화면을 게시글 목록으로 연결하는 @GetMapping("/") 매핑을 추가했습니다.

둘째, 기존 검색 분기 로직의 null 체크를 StringUtils.hasText()로 교체했습니다.
검색 폼에서 아무것도 입력하지 않으면 null이 아닌 빈 문자열 ""이 전달되기 때문에,
== null만으로는 "입력 없음"을 제대로 감지할 수 없는 문제가 있었습니다.

셋째, 제목과 내용을 동시에 검색하는 통합 검색 파라미터 searchKeywordTotal을 추가했습니다.
기존의 제목 단독, 내용 단독 검색과 분리해 각각 독립적으로 동작하도록 분기를 재구성했습니다.

Step 2

무엇이 변경되었는가

BoardController.java

변경이 가장 많은 파일입니다. 세 가지가 추가·수정되었습니다.

  • @GetMapping("/") 매핑 추가 — /board/list로 redirect
  • boardlist 메서드에 String searchKeywordTotal 파라미터 추가
  • if/else 분기 조건을 == null에서 StringUtils.hasText()로 교체, 분기 순서 재구성
  • model.addAttribute("searchKeywordTotal", searchKeywordTotal) 추가

boardlist.html

검색 폼의 첫 번째 input name이 searchKeywordContent에서 searchKeywordTotal로 수정되었습니다.
페이징 링크에도 searchKeywordTotal이 포함되어 페이지를 넘겨도 통합 검색어가 유지됩니다.

Step 3

핵심 코드 설명

① @GetMapping("/") — 초기 화면 redirect

BoardController.java

@GetMapping("/")
public String index(){
    return "redirect:/board/list";
}

http://localhost:8080/으로 접속했을 때 처음 만나는 매핑입니다.
메서드 이름 index는 관례입니다. 웹 서버에서 기본 페이지를 index.html이라 부르는 것과 같은 맥락으로, home()을 쓰기도 합니다. Spring이 이름에 의미를 부여하지는 않습니다.

왜 return "boardlist"가 아니라 "redirect:/board/list"인가

return "boardlist"를 하면 Thymeleaf가 boardlist.html을 렌더링하려 합니다.
그런데 boardlist.html은 ${list}, ${nowPage} 같은 모델 데이터가 없으면 렌더링 중 오류가 납니다.
index() 메서드는 그 데이터를 채워주지 않기 때문에 Whitelabel Error가 떴습니다.

redirect:를 붙이면 브라우저가 /board/list로 다시 요청을 보냅니다.
그러면 데이터를 채워주는 boardlist 메서드가 실행되어 정상적으로 화면이 나옵니다.

② StringUtils.hasText() — null과 빈 문자열 동시 처리

BoardController.java

// 이전: null만 체크
if(searchKeywordTitle == null && searchKeywordContent == null){
    list = boardService.boardList(pageable);
}

// 현재: null과 "" 모두 처리
if(!StringUtils.hasText(searchKeywordTitle) && StringUtils.hasText(searchKeywordContent)){
    list = boardService.boardSearchContentList(searchKeywordContent, pageable);
}
else if(StringUtils.hasText(searchKeywordTitle) && !StringUtils.hasText(searchKeywordContent)){
    list = boardService.boardSearchTitleList(searchKeywordTitle, pageable);
}
else if(StringUtils.hasText(searchKeywordTotal)){
    list = boardService.boardSearchTotalList(searchKeywordTotal, pageable);
}
else{
    list = boardService.boardList(pageable);
}

StringUtils.hasText()는 다음 세 가지를 모두 false로 처리합니다.

  • null
  • "" (빈 문자열)
  • " " (공백만 있는 문자열)

왜 form에서 빈 입력이 null이 아닌 ""로 오는가

HTML form의 input이 화면에 존재하는 이상, 사용자가 아무것도 입력하지 않아도 name=""의 필드는 항상 전송됩니다.
입력값이 없으면 name=(값 없음), 즉 빈 문자열 ""로 전달됩니다.
null이 되는 경우는 URL에 해당 파라미터 자체가 아예 없을 때입니다.

HTTP 요청

// 검색어 입력 없이 검색 버튼 누름
GET /board/list?searchKeywordTotal=&searchKeywordTitle=&searchKeywordContent=
//                              ↑ 빈 문자열 ""

// 주소창에 직접 /board/list 입력
GET /board/list
// searchKeywordTitle 파라미터 자체 없음 → null

StringUtils.isEmpty()를 쓰면 !가 필요 없다

StringUtils.hasText()는 "텍스트가 있는가?"를 확인하므로, 없는 경우를 체크하려면 !를 붙여야 합니다.
Spring의 StringUtils.isEmpty()는 반대 방향이라 ! 없이 "없는가?"를 바로 표현할 수 있습니다.

BoardController.java — 대안 방식

// hasText + ! 방식
if (!StringUtils.hasText(searchKeywordTitle)) { ... }

// isEmpty 방식 (! 없이 동일 의미)
if (StringUtils.isEmpty(searchKeywordTitle)) { ... }

단, isEmpty()는 null과 ""만 처리합니다. 공백 문자열(" ")은 비어있지 않다고 판단합니다.
사용자가 공백만 입력했을 때도 처리하려면 hasText()가 더 안전합니다.

③ findByTitleContainingOrContentContaining — 파라미터 2개

BoardRepository.java

Page<Board> findByTitleContainingOrContentContaining(
    String searchKeywordTitle,
    String searchKeywordContent,
    Pageable pageable
);

JPA 쿼리 메서드에서 Or는 SQL의 OR 조건입니다.
Or 조건이 하나 추가될 때마다 파라미터도 하나씩 늘어납니다.

실행되는 SQL

WHERE title LIKE '%검색어%' OR content LIKE '%검색어%'

SQL에서 OR 양쪽이 각각 별개의 값을 비교하기 때문에, Java 메서드도 파라미터를 2개 받아야 합니다.
동일한 키워드로 제목과 내용을 동시에 검색하더라도 searchKeywordTotal을 두 번 넘겨야 합니다.

BoardService.java

public Page<Board> boardSearchTotalList(String searchKeywordTotal, Pageable pageable){
    return boardRepository.findByTitleContainingOrContentContaining(
        searchKeywordTotal,   // title 검색어
        searchKeywordTotal,   // content 검색어 (같은 값을 두 번)
        pageable
    );
}

Or 말고 And도 있나?

findByTitleContainingAndContentContaining도 존재합니다.
Or와 And는 완전히 다른 결과를 냅니다.

실행되는 SQL 비교

// Or — 제목 또는 내용 중 하나라도 포함
WHERE title LIKE '%Spring%' OR content LIKE '%Spring%'
// → "Spring"이 제목에만 있어도, 내용에만 있어도 결과에 포함

// And — 제목과 내용 둘 다 포함
WHERE title LIKE '%Spring%' AND content LIKE '%Spring%'
// → "Spring"이 제목과 내용 모두에 있어야만 결과에 포함

통합 검색처럼 "어느 곳이든 포함되면 보여줘"는 Or가 맞습니다.
파라미터 개수 규칙은 동일합니다. And도 조건이 2개이므로 파라미터 2개가 필요합니다.

Step 4

왜 이렇게 작성했는가

왜 초기 화면을 redirect로 처리하는가

BoardController.java

@GetMapping("/")
public String index(){
    return "redirect:/board/list";
}

boardlist.html은 렌더링에 list, nowPage, startPage, endPage 데이터가 필요합니다.
이 데이터를 채워주는 건 boardlist() 메서드이지, index()가 아닙니다.
index()에서 직접 boardlist.html을 리턴하면 데이터 없이 템플릿이 열려 오류가 납니다.

redirect:를 붙이면 브라우저가 /board/list로 새 요청을 보냅니다.
그 요청을 boardlist()가 받아서 데이터를 채운 뒤 boardlist.html을 렌더링합니다.
역할이 명확히 분리됩니다.

모델 데이터가 필요 없는 템플릿이라면 return "boardlist"해도 되나?

템플릿에 ${list} 같은 모델 데이터가 전혀 없다면 return "boardlist"를 해도 오류는 나지 않습니다.
하지만 루트 URL(/)에서는 redirect를 쓰는 것이 관례입니다. 이유가 있습니다.

  • URL 일관성 — redirect 후 브라우저 주소창이 /board/list로 바뀝니다. 북마크나 링크 공유가 의미 있어집니다.
  • 책임 분리 — index()는 "어디로 가라"만 담당합니다. 렌더링 책임은 boardlist()에 있습니다.
  • 나중을 위해 — 지금은 데이터가 없어도, 나중에 템플릿이 바뀌어 데이터가 필요해질 수 있습니다. redirect면 index()를 건드릴 필요가 없습니다.

결론: 데이터가 없어도 return "boardlist"는 동작하지만, 루트 URL에서는 redirect가 더 올바른 설계입니다.

왜 null 체크만으로는 부족한가

BoardController.java

// ❌ 이전: form에서 아무것도 입력 않아도 통과 못함
if(searchKeywordTitle == null && searchKeywordContent == null){
    list = boardService.boardList(pageable);
}

검색 폼에서 아무것도 입력하지 않고 검색 버튼을 누르면 URL이 이렇게 됩니다.

HTTP 요청

GET /board/list?searchKeywordTotal=&searchKeywordTitle=&searchKeywordContent=

파라미터가 URL에 존재하지만 값이 없는 상태, 즉 ""가 전달됩니다.
searchKeywordTitle == null은 ""에 대해 false를 반환합니다.
결과적으로 전체 목록 분기를 타지 못하고 검색 분기로 빠져버립니다.

StringUtils.hasText()는 null과 "" 둘 다 false로 처리하기 때문에,
"아무것도 입력하지 않은 상태"를 정확하게 판단할 수 있습니다.

💡 개선 포인트

boardWritePro의 제목/내용 검증도 지금은 StringUtils.hasText()로 직접 분기하고 있습니다.
나중에 @NotBlank, @Valid (Bean Validation)를 배우면 이 if/else 검증 코드를 어노테이션 하나로 대체할 수 있습니다.

왜 검색 분기의 순서가 바뀌었는가

BoardController.java

if(!StringUtils.hasText(searchKeywordTitle) && StringUtils.hasText(searchKeywordContent)){
    // 내용만 입력된 경우
}
else if(StringUtils.hasText(searchKeywordTitle) && !StringUtils.hasText(searchKeywordContent)){
    // 제목만 입력된 경우
}
else if(StringUtils.hasText(searchKeywordTotal)){
    // 통합 검색어가 입력된 경우
}
else{
    // 아무것도 입력 없음 → 전체 목록
}

이전에는 전체 목록을 첫 번째 분기로 처리했습니다.
searchKeywordTotal이 추가되면서 "아무것도 없음" 조건이 마지막 else로 밀렸습니다.
제목/내용 각각을 먼저 체크하고, 그다음 통합 검색을 체크하고, 그래도 아무것도 없으면 전체 목록을 반환하는 구조입니다.

💡 개선 포인트

현재 분기에서 제목과 내용을 동시에 입력하면 어느 분기도 해당하지 않아 전체 목록이 반환됩니다.
지금 UI에서는 두 필드를 동시에 입력할 일이 없으니 당장 버그는 아닙니다.
나중에 검색 UI가 바뀐다면 이 케이스에 대한 분기를 추가해야 합니다.

if/else if에서 순서 자체가 로직이다

만약 통합 검색 분기를 제일 위로 올리면 어떻게 될까요?

BoardController.java — 순서가 잘못된 경우

// ❌ 통합 검색을 먼저 체크하면
if(StringUtils.hasText(searchKeywordTotal)){
    list = boardService.boardSearchTotalList(searchKeywordTotal, pageable);
}
// 제목만 입력해도 여기 절대 못 들어옴 (통합 검색 분기에서 걸림)
else if(StringUtils.hasText(searchKeywordTitle) && !StringUtils.hasText(searchKeywordContent)){
    list = boardService.boardSearchTitleList(searchKeywordTitle, pageable);
}

제목 검색창에 "Spring"을 입력해도 통합 검색 분기로 들어가버립니다.
if/else if는 위에서부터 순서대로 평가하기 때문에, 분기 순서 자체가 비즈니스 로직입니다.
코드가 동작하더라도 순서가 의도와 다르면 전혀 다른 결과가 나올 수 있습니다.

왜 Or 조건 쿼리 메서드는 파라미터가 2개인가

BoardRepository.java

Page<Board> findByTitleContainingOrContentContaining(
    String title, String content, Pageable pageable
);

JPA 쿼리 메서드는 메서드 이름에 등장하는 조건 키워드 개수만큼 파라미터를 필요로 합니다.
TitleContaining 하나, ContentContaining 하나 — 두 조건이므로 파라미터도 두 개입니다.
SQL로 보면 이렇게 대응됩니다.

실행되는 SQL

WHERE title LIKE '%:title%'   -- 첫 번째 파라미터
   OR content LIKE '%:content%'  -- 두 번째 파라미터

동일한 키워드로 검색하더라도 SQL 구조상 각 컬럼에 별도 파라미터가 필요합니다.
그래서 boardSearchTotalList("Spring", pageable)처럼 하나만 받아도,
내부에서는 findByTitleContainingOrContentContaining("Spring", "Spring", pageable)으로 같은 값을 두 번 넘깁니다.

💡 개선 포인트

같은 값을 두 번 넘기는 구조가 어색하다면, @Query로 직접 JPQL을 작성하면 파라미터를 하나로 줄일 수 있습니다.

BoardRepository.java — @Query 방식

@Query("SELECT b FROM Board b WHERE b.title LIKE %:keyword% OR b.content LIKE %:keyword%")
Page<Board> findByKeyword(@Param("keyword") String keyword, Pageable pageable);

Step 7

초보자가 하기 쉬운 착각

검색어를 비우고 검색하면 null이 들어온다?

아닙니다. HTML form의 input은 화면에 있는 이상 항상 전송됩니다.
입력값이 없으면 빈 문자열 ""이 전달됩니다.
null이 오는 경우는 URL에 파라미터 자체가 없을 때입니다.
예를 들어 주소창에 /board/list를 직접 입력하면 파라미터가 없으니 null이 됩니다.

isEmpty()와 hasText()는 완전히 같은가?

아닙니다. 공백 문자열 " " 처리가 다릅니다.
isEmpty(" ")는 false입니다. 공백도 문자열로 봅니다.
hasText(" ")는 false입니다. 공백만 있으면 텍스트가 없다고 봅니다.
사용자가 공백만 입력했을 때도 "입력 없음"으로 처리하고 싶다면 hasText()가 더 적합합니다.

Or 조건 메서드는 파라미터가 하나여도 되지 않나?

안 됩니다. JPA는 메서드 이름에 등장한 조건 키워드 개수만큼 파라미터를 요구합니다.
TitleContaining과 ContentContaining이 각각 하나씩이므로 파라미터 2개가 필수입니다.
파라미터를 1개로 선언하면 앱 실행 시점에 오류가 납니다.

redirect는 항상 써야 하는가?

아닙니다. index()처럼 직접 모델 데이터를 채우지 않고 다른 메서드의 처리 결과가 필요할 때만 씁니다.
boardWriteForm()처럼 데이터 없이 HTML만 보여주면 되는 경우는 return "boardwrite"로 충분합니다.
redirect를 무조건 쓰면 불필요한 HTTP 왕복이 생깁니다.

Step 9

오늘 배운 것

  • HTML form에서 빈 입력을 제출하면 null이 아닌 빈 문자열 ""이 전달된다.
  • StringUtils.hasText()는 null, "", 공백 문자열을 모두 false로 처리한다.
  • StringUtils.isEmpty()를 쓰면 ! 없이 "비어있는 경우"를 표현할 수 있다. 단 공백 문자열은 처리하지 못한다.
  • return "redirect:/경로"는 브라우저가 해당 경로로 다시 GET 요청을 보내게 한다.
  • 데이터가 필요한 템플릿을 직접 리턴하면 오류가 난다. 데이터를 채워주는 매핑으로 redirect해야 한다.
  • JPA Or 조건 쿼리 메서드는 조건 개수만큼 파라미터가 필요하다. 같은 키워드라도 두 번 넘겨야 한다.
  • 검색 파라미터를 모델에 추가해야 페이지를 이동해도 검색어가 유지된다.
Step 10

이해도 확인 질문

  1. 검색 폼에서 아무것도 입력하지 않고 검색 버튼을 눌렀을 때 컨트롤러 파라미터에 어떤 값이 들어오는가?

    null이 아닌 빈 문자열 ""이 들어옵니다. HTML form의 input은 화면에 존재하는 이상 항상 전송되기 때문입니다. 파라미터 자체가 URL에 없는 경우에만 null이 됩니다.

  2. @GetMapping("/")에서 return "boardlist"가 아닌 return "redirect:/board/list"를 써야 하는 이유는?

    boardlist.html은 list, nowPage 등 모델 데이터가 없으면 렌더링 오류가 납니다. index()는 그 데이터를 채워주지 않으므로 직접 템플릿을 리턴하면 안 됩니다. redirect로 /board/list에 새 요청을 보내면 boardlist() 메서드가 데이터를 채운 뒤 정상 렌더링합니다.

  3. findByTitleContainingOrContentContaining에 파라미터가 2개 필요한 이유는?

    JPA 쿼리 메서드는 조건 키워드 개수만큼 파라미터를 요구합니다. TitleContaining과 ContentContaining이 각각 하나씩이라 파라미터도 2개입니다. SQL의 title LIKE '%?%' OR content LIKE '%?%' 각각에 값을 바인딩하기 때문입니다.

  4. StringUtils.hasText()와 == null의 차이는?

    == null은 null인 경우만 true입니다. StringUtils.hasText()는 null, "", " "(공백만 있는 문자열)을 모두 false로 처리합니다. 검색어가 없는 상태를 정확히 판단하려면 hasText()가 더 안전합니다.

  5. 통합 검색으로 "Spring"을 검색했을 때 boardSearchTotalList 내부에서 repository에 어떤 값이 전달되는가?

    findByTitleContainingOrContentContaining("Spring", "Spring", pageable)처럼 같은 값이 두 번 전달됩니다. Or 조건 양쪽에 각각 파라미터가 필요하기 때문에, 동일한 키워드라도 두 번 넘겨야 합니다.

Step 12

다음 커밋을 위한 준비

  • 입력값 검증 위치 — "제목이 비어있는가?"는 비즈니스 로직이 아니라 입력값 형식 검증입니다. Controller에서 처리하는 것이 원칙입니다. Service는 올바른 데이터가 들어온다고 가정하고 동작합니다.
  • 비즈니스 로직 vs 입력값 검증 — "공지글은 관리자만 작성 가능하다"처럼 서비스가 정한 규칙은 Service에 둡니다. "제목을 입력했는가?"처럼 형식 문제는 Controller에 둡니다.
  • Bean Validation — @NotBlank, @Valid를 사용하면 Controller에 if 문 없이 검증 코드를 깔끔하게 처리할 수 있습니다. 지금 방식으로 흐름을 이해한 뒤 나중에 배우면 더 잘 이해됩니다.
  • 파일 없을 때 처리 — 현재 게시글 작성 시 파일이 없어도 오류 없이 저장되도록 수정이 필요합니다. file.isEmpty()로 파일 존재 여부를 확인하는 분기를 추가해보세요.
