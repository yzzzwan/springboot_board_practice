Step 3

핵심 코드 설명

① @GetMapping("board/modify/{id}") — 수정 폼 열기

@GetMapping("board/modify/{id}")
public String boardUpdate(@PathVariable("id") Integer id, Model model) {
    model.addAttribute("board", boardService.boardView(id));
    return "boardmodify";
}

@PathVariable이란?

URL 경로 안의 {id} 부분을 메서드 파라미터로 꺼내오는 어노테이션입니다.

?id=3처럼 쿼리 파라미터로 받는 방식과 달리, URL 경로 자체에 값이 포함됩니다.

@PathVariable vs @RequestParam

어노테이션URL 예시언제 쓰는가
@PathVariable/board/modify/3리소스를 식별할 때. "3번 게시글"처럼 대상이 명확한 경우. RESTful URL 설계에 사용.
@RequestParam/board/list?page=2검색 조건, 페이지 번호, 필터 등 옵션값을 전달할 때. 없어도 기본값으로 동작 가능.
 
// @PathVariable — URL 경로로 값 받기
@GetMapping("/board/modify/{id}")
public String modify(@PathVariable("id") Integer id) { ... }
// 요청: /board/modify/3  →  id = 3

// @RequestParam — 쿼리 파라미터로 값 받기
@GetMapping("/board/list")
public String list(@RequestParam(defaultValue = "0") int page) { ... }
// 요청: /board/list?page=2  →  page = 2
// 요청: /board/list         →  page = 0 (기본값)
이 프로젝트의 /board/view?id=2 는 RESTful 관점에서 어떤가?

RESTful 설계에서는 특정 리소스를 식별할 때 경로 변수를 씁니다.
"2번 게시글"처럼 대상이 명확한 경우라면 /board/view/2가 더 정확한 표현입니다.

현재 프로젝트는 /board/view?id=2 방식을 쓰고 있는데, 이는 틀린 게 아닙니다.
@PathVariable 없이 Spring이 자동 바인딩하는 방식을 먼저 보여주려는 학습 목적으로 이해하면 됩니다.
실무에서는 상세 조회를 /board/{id} 형태로 구현하는 경우가 많습니다.

② @PostMapping("/board/update/{id}") — 수정 저장 처리

@PostMapping("/board/update/{id}")
public String boardUpdate(@PathVariable("id") Integer id, Board board) {
    Board boardTemp = boardService.boardView(id);  // ① DB에서 기존 데이터 조회
    boardTemp.setTitle(board.getTitle());           // ② 제목 덮어씌우기
    boardTemp.setContent(board.getContent());       // ③ 내용 덮어씌우기
    boardService.boardWrite(boardTemp);             // ④ save() 호출
    return "redirect:/board/list";
}

여기서 가장 중요한 부분은 boardService.boardWrite(boardTemp)입니다.
boardWrite()는 repository.save()를 호출하는데, save()는 전달받은 객체에 ID가 있으면 UPDATE, 없으면 INSERT를 수행합니다.

③ boardmodify.html — 기존 값을 폼에 채워넣기

<form th:action="@{/board/update/{id}(id=${board.id})}" method="post">
    <input name="title" type="text" placeholder="제목" th:value="${board.title}">
    <textarea name="content" placeholder="내용" th:text="${board.content}"></textarea>
    <button type="submit">수정</button>
</form>
  • th:action — 폼이 제출될 URL을 Thymeleaf로 동적으로 설정. /board/update/3 형태로 만들어집니다.
  • th:value — input의 초기값 설정. 기존 제목이 미리 채워집니다.
  • th:text — textarea의 초기 텍스트 설정. 기존 내용이 미리 채워집니다.

Thymeleaf URL 문법 — 경로 변수 vs 쿼리 파라미터

이 프로젝트에서 두 가지 URL 표현 방식이 혼재합니다.
괄호 안 이름이 {}로 감싼 경로 변수 이름과 일치하면 경로 변수로, 아니면 쿼리 파라미터로 붙습니다.

Thymeleaf 표현식생성되는 URL방식
@{/board/update/{id}(id=${board.id})}/board/update/3경로 변수 — {id}에 값이 들어감
@{/board/delete(id=${board.id})}/board/delete?id=3쿼리 파라미터 — URL에 {}가 없어 ?로 붙음

컨트롤러에서 받는 방법도 달라집니다.

// 경로 변수로 받는 경우 → @PathVariable
@GetMapping("/board/update/{id}")
public String update(@PathVariable("id") Integer id) { ... }

// 쿼리 파라미터로 받는 경우 → 파라미터 직접 바인딩
@GetMapping("/board/delete")
public String delete(Integer id) { ... }
Step 4

왜 이렇게 작성했는가?

왜 URL에 {id}를 포함시켰는가?

수정할 게시글이 어떤 글인지 서버에 알려줘야 합니다.
POST 요청으로 폼 데이터만 보내면 서버는 "몇 번 글을 수정해야 하는지" 알 수 없습니다.
URL 경로에 id를 포함시켜 명확하게 전달합니다.

왜 DB에서 다시 조회한 뒤(boardTemp) title/content를 복사하는가?

@PathVariable로 id를 받고 있으니 board.setId(id)를 해서 바로 save(board)하면 안 되나 생각할 수 있습니다.

폼에서 넘어온 board 객체에는 폼에서 입력한 title, content만 바인딩되고, 나머지 필드(예: createDate, 작성자 등)는 모두 null입니다.
그 상태로 save()를 호출하면 기존에 있던 값들이 null로 덮어씌워집니다.

DB에서 기존 객체 전체를 먼저 꺼내온 뒤, 수정할 값만 골라서 바꾸는 방식이 안전합니다.
현재 엔티티는 id/title/content만 있어서 큰 차이가 없지만, 필드가 늘어날수록 이 패턴이 중요해집니다.

boardService.boardWrite(boardTemp)를 호출하지 않으면?

DB에 아무것도 저장되지 않습니다.

boardTemp.setTitle(), boardTemp.setContent()는 Java 메모리 안에서만 값을 바꿉니다.

현재 컨트롤러 메서드에는 @Transactional이 없으므로 JPA 변경 감지(Dirty Checking)도 작동하지 않습니다.

save()를 빠뜨리면 redirect는 정상적으로 되지만 DB는 전혀 수정되지 않습니다.

왜 이 방식은 권장되지 않는가? — JPA 변경 감지(Dirty Checking)

참고

JPA에서는 수정할 때 이렇게 덮어씌워버리는 방식을 절대 사용하면 안 됩니다.

JPA에는 변경 감지(Dirty Checking)라는 기능이 있어서 트랜잭션 내에서 DB에서 불러온 엔티티에 수정이 이뤄질 경우, 트랜잭션이 끝날 때 자동으로 DB에 반영됩니다.

JPA에는 변경 감지(Dirty Checking)라는 기능이 있습니다.

현재 코드는 동작은 하지만 JPA를 더 공부할 때 @Transactional + 변경 감지 방식을 꼭 학습하세요.
그리고 JPA 변경 감지, JPA merge, JPA persist도 따로 학습하세요.

변경 감지를 사용한 코드 예시 (나중에 배울 방법)

// BoardService.java
@Transactional
public void boardUpdate(Integer id, Board newBoard) {
    Board board = boardRepository.findById(id).get();
    board.setTitle(newBoard.getTitle());
    board.setContent(newBoard.getContent());
    // save() 호출 없음!
    // 트랜잭션이 끝나는 시점에 JPA가 변경을 감지하고 자동으로 UPDATE 실행
}

Step 7

초보자가 하기 쉬운 착각

save()는 항상 INSERT(새로 저장)를 한다고 생각하기 쉽습니다.

save()는 id 유무에 따라 동작이 달라집니다. id가 있으면 UPDATE, 없으면 INSERT입니다.

이 원리를 이해하지 못하면 "왜 수정했는데 새 글이 생기지?" 같은 버그를 만납니다.

@PathVariable과 @RequestParam을 혼동하기 쉽습니다.

@PathVariable은 /board/modify/3처럼 URL 경로 안에 값이 있을 때 사용합니다.

@RequestParam은 /board/list?page=2처럼 쿼리 파라미터로 전달할 때 사용합니다.

JPA에서 save()를 호출해야 저장된다고 생각하기 쉽습니다.

변경 감지(Dirty Checking) 방식에서는 @Transactional 안에서 값을 바꾸기만 하면 트랜잭션이 끝날 때 JPA가 자동으로 UPDATE를 실행합니다.

save() 없이도 됩니다.

Step 9

오늘 배운 것

  • @PathVariable로 URL 경로 안의 값을 메서드 파라미터로 받을 수 있다
  • 수정 기능은 GET(폼 표시)과 POST(저장 처리) 두 단계로 구성된다
  • save()는 id가 있으면 UPDATE, 없으면 INSERT를 실행한다
  • 폼에서 넘어온 객체에는 id가 없으므로 DB에서 기존 객체를 먼저 조회해야 한다
  • JPA의 정석적인 수정 방법은 save() 직접 호출이 아닌 변경 감지(Dirty Checking)다
Step 10

이해도 확인 질문

  1. /board/modify/5 요청이 들어왔을 때 숫자 5를 컨트롤러에서 어떻게 받는가?

    @PathVariable("id") Integer id 로 받습니다. URL 경로의 {id} 부분과 어노테이션 이름이 매핑되어 자동으로 값이 주입됩니다.

  2. 폼에서 넘어온 board 객체를 바로 save(board) 하지 않고, DB에서 한 번 더 조회한 뒤 저장하는 이유는?

    폼에서 넘어온 board에는 id가 없습니다. id 없이 save()를 호출하면 UPDATE 대신 INSERT가 실행되어 새 글이 생성됩니다. DB에서 id가 있는 객체를 먼저 꺼내와야 save()가 UPDATE로 동작합니다.

  3. JPA 변경 감지(Dirty Checking)란 무엇인가?

    트랜잭션 내에서 DB로부터 조회한 엔티티를 수정하면, 트랜잭션이 끝날 때 JPA가 처음 조회 시점의 상태와 현재 상태를 비교해서 변경된 부분을 자동으로 UPDATE 해주는 기능입니다. save()를 직접 호출하지 않아도 됩니다.

  4. th:value와 th:text의 차이는?

    th:value는 input 태그의 value 속성을 설정합니다(폼 입력 초기값). th:text는 태그 사이의 텍스트 내용을 설정합니다. textarea는 value 속성이 없고 태그 사이 내용이 값이 되므로 th:text를 사용합니다.

  5. GET 요청과 POST 요청을 수정 기능에서 분리하는 이유는?

    HTTP 설계 원칙상 GET은 데이터를 조회하는 용도, POST는 데이터를 변경/생성하는 용도입니다. GET으로 폼을 보여주고 POST로 처리하면 역할이 명확하게 분리되고, 브라우저 새로고침 시 중복 제출 문제도 방지됩니다.

Step 11

작은 실습

생각해보기 — 수정 시 작성일은 어떻게 유지할까?

현재 수정 폼(boardmodify.html)에는 작성일 필드가 없습니다. 만약 Board 엔티티에 createDate 필드를 추가한다면 수정 시 날짜가 초기화되는 문제가 생길 수 있습니다.

다음 질문에 직접 생각해보세요:

수정 시 제목과 내용만 바꾸고 작성일은 유지하려면 현재 코드에서 어떻게 해야 할까요?

힌트: boardTemp.setTitle() / boardTemp.setContent()만 하고 setCreateDate()는 하지 않으면 됩니다. DB에서 꺼낸 boardTemp의 createDate는 이미 원래 값이기 때문입니다.

Step 12

다음 Commit을 위한 준비

  • 페이징(Paging) — 게시글이 많아지면 목록을 여러 페이지로 나눠야 합니다. Spring Data JPA의 Pageable을 공부해두세요.
  • JPA @Transactional — 변경 감지를 올바르게 쓰려면 트랜잭션 개념이 필요합니다.
  • Spring Data JPA Page<T> — 페이징 결과를 담는 객체입니다.
  • Thymeleaf 페이징 링크 — th:href로 페이지 번호 링크를 동적으로 생성하는 방법을 미리 생각해보세요.
