Step 1

이번 Commit 한눈에 보기

지금까지 게시글 목록은 볼 수 있었는데, 제목을 클릭해도 아무 데도 이동하지 않았어. 이번 커밋에서 게시글 상세 페이지를 만들었어.

목록에서 제목을 클릭하면 ?id=1 같은 URL로 이동하고, 해당 게시글의 내용을 DB에서 가져와서 화면에 표시하는 흐름이야.

이번 commit으로 목록(전체 조회)과 상세(1개 조회)가 연결되어 전형적인 게시판 구조가 완성되었어.

Step 3

핵심 코드 설명

Integer id 파라미터 — URL 파라미터 자동 주입

public String boardView(Model model, Integer id){

URL에 ?id=1이라고 붙으면, Spring이 알아서 메서드 파라미터 Integer id에 1을 넣어줘. URL 파라미터는 원래 전부 문자열로 넘어오는데, Integer id라고 선언하면 Spring이 문자열 → 정수 변환까지 자동으로 해줘.

// Spring 없이 직접 파싱하면 이렇게 해야 함 (서블릿 방식)
String idStr = request.getParameter("id"); // "1" (문자열)
Integer id = Integer.parseInt(idStr);       // 문자열 → 정수 변환

Spring이 이 과정을 대신 해주기 때문에 그냥 Integer id만 선언하면 돼.

파라미터 순서는 상관없다

Spring은 파라미터를 이름과 타입으로 주입하기 때문에 순서가 달라도 동작해.

// 둘 다 동작
public String boardView(Model model, Integer id){ ... }
public String boardView(Integer id, Model model){ ... }

// Spring이 판단하는 방식
// Integer id  → "URL에 ?id= 파라미터 있네, 여기 넣자"
// Model model → "Model 타입이네, Spring이 만들어서 여기 넣자"

쿼리 파라미터 vs Path Variable

// 쿼리 파라미터 방식 — 현재 프로젝트
// URL: /board/view?id=3
@GetMapping("/board/view")
public String boardView(Integer id){ }

// Path Variable 방식
// URL: /board/view/3
@GetMapping("/board/view/{id}")
public String boardView(@PathVariable Integer id){ }

/board/view?id=3은 쿼리 파라미터, /board/view/3은 경로 변수야. /board/view/id=3 이런 형식은 없어 — 저렇게 쓰면 id=3이라는 이름의 경로로 인식돼서 의도한 대로 동작하지 않아.

Repository 메서드별 반환 타입 비교

메서드반환 타입이유
save(board)Board항상 저장됨. 실패 가능성 없음
findAll()List<Board>항상 존재 (게시글 없으면 빈 리스트)
findById(id)Optional<Board>해당 id가 DB에 없을 수 있음
deleteById(id)void삭제 후 남는 게 없음

findById(id).get() — Optional 이해

return boardRepository.findById(id).get();

Optional은 Java에서 제공하는 클래스(타입)야. "값을 담을 수도 있고, 비어있을 수도 있는 상자"야. null이 아니라 "비어있다는 상태를 명시적으로 표현하는 객체"야.

Optional<Board> result = boardRepository.findById(999); // 없는 id

result == null         // false — null이 아님
result.isPresent()     // false — 비어있음
result.isEmpty()       // true  — 비어있음
result.get()           // 💥 NoSuchElementException 발생!

값이 없을 때 .get()을 호출하면 에러가 발생해. 이건 일부러 에러를 내는 게 아니라, 실수로 발생하는 나쁜 에러야. 올바른 방법은 값이 있는지 먼저 확인하거나 orElseThrow()를 쓰는 거야.

// ❌ 지금 코드 — 값 없으면 에러 터짐 (학습용으로만 OK)
return boardRepository.findById(id).get();

// ✅ 올바른 방법 — 없으면 명시적으로 예외 던지기
return boardRepository.findById(id)
    .orElseThrow(() -> new RuntimeException("게시글이 없습니다"));

save()는 id를 새로 만들어서 반환한다

Board board = new Board();
board.setTitle("제목");

System.out.println(board.getId()); // null — 아직 id 없음

Board saved = boardRepository.save(board);

System.out.println(saved.getId()); // 1 — DB가 id를 만들어서 채워줌
System.out.println(board.getId()); // 1 — 원본 객체에도 반영됨

저장 전 Board는 id가 없어. DB에 저장될 때 AUTO_INCREMENT로 id가 자동 생성되고, save()는 id가 채워진 Board를 반환해. 지금 프로젝트에서는 저장 후 id를 쓸 일이 없어서 반환값을 무시하고 있어.

th:href="@{...}" — Thymeleaf URL 파라미터

<a th:text="${board.title}" th:href="@{/board/view(id=${board.id})}"></a>

@{경로(파라미터=값)} 방식을 쓰면 Thymeleaf가 ?와 &를 자동으로 붙여줘. URL 인코딩(한글, 특수문자 → %EC%...)도 자동 처리해줘서 더 안전해.

<!-- 파라미터 여러 개 — 쉼표로 이어쓰면 됨 -->
th:href="@{/board/view(id=${board.id}, page=${page}, sort=${sort})}"
<!-- 결과: /board/view?id=1&page=2&sort=desc -->

<!-- 직접 쓰는 방식 — 동작은 하지만 인코딩 처리 없음 -->
th:href="@{/board/view?id=${board.id}}"
Step 4

왜 이렇게 작성했는가?

왜 URL에 id를 담는가?

어떤 게시글을 보여줄지 서버에 알려줘야 하기 때문이야. ?id=1이 없으면 서버는 "몇 번 게시글을 달라는 거지?"를 알 수 없어.

왜 findAll()이 아니라 findById()인가?

// findAll() → 전체 조회 (목록 페이지용)
List<Board> list = boardRepository.findAll();

// findById(id) → 1개 조회 (상세 페이지용)
Optional<Board> board = boardRepository.findById(id);

상세 페이지에서 전체를 다 가져오면 낭비야. id로 딱 1개만 정확히 가져오는 게 맞아.

왜 Service를 거치는가?

Controller는 HTTP 요청/응답만 담당하고, 데이터를 가져오는 로직은 Service에 위임하는 구조를 유지하는 거야. 나중에 비즈니스 로직이 복잡해질 때 Controller가 지저분해지지 않아.

에러는 어디서 처리하는가?

역할에 따라 나눠서 처리해.

// Service — 예외를 던지는 역할
public Board boardView(Integer id){
    return boardRepository.findById(id)
        .orElseThrow(() -> new RuntimeException("게시글이 없습니다"));
}

// Controller — 그냥 통과 (예외를 위로 올려보냄)
public String boardView(Model model, Integer id){
    model.addAttribute("board", boardService.boardView(id));
    return "boardview";
}

// @ControllerAdvice — 실제 처리 (별도 클래스)
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(RuntimeException.class)
    public String handle(RuntimeException e, Model model){
        model.addAttribute("message", e.getMessage());
        return "error"; // error.html 보여줌
    }
}

예외 처리는 @ControllerAdvice 전역 핸들러 클래스에서 하는 게 일반적이야. Controller마다 따로 짜지 않고 한 곳에서 모든 예외를 관리할 수 있어. 지금 단계에서 몰라도 되는 내용이고, 수정/삭제 기능 붙이고 나서 배우면 딱 맞는 타이밍이야.

Step 7

초보자가 하기 쉬운 착각

Integer id 이름은 URL 파라미터 이름과 같아야 한다 URL의 ?id=와 메서드 파라미터 Integer id의 이름이 같아야 Spring이 자동으로 연결해줘. 이름이 다르면 @RequestParam("id") Integer myId처럼 명시해줘야 해.
.get()이 항상 안전한 건 아니다 findById()가 결과를 못 찾으면 Optional이 비어있어. 이때 .get()을 호출하면 NoSuchElementException이 발생해. 실무에서는 .orElseThrow()를 사용해 적절한 에러 처리를 해줘야 해.
findById()와 findAll()의 반환 타입이 다르다 findAll()은 List<Board>를 반환하고, findById()는 Optional<Board>를 반환해. 타입이 다르기 때문에 처리 방법도 달라야 해.
URL에 ?가 붙는다고 GET인 게 아니다 ?는 URL에 데이터를 붙이는 문법일 뿐이야. GET인지 POST인지는 @GetMapping / @PostMapping으로 결정돼. POST도 URL에 ?를 붙일 수는 있지만, 보통 Body에 담는 게 목적이라 잘 안 써.
@GetMapping에 ? 뒤 파라미터는 쓰지 않는다 @GetMapping("/board/view")에는 경로만 써. ?id=1 같은 파라미터는 메서드 파라미터(Integer id)로 받는 거야. Path Variable은 경로의 일부라서 @GetMapping("/board/view/{id}")처럼 명시해야 해.
같은 URL이어도 GET/POST 다르면 다른 메서드가 실행된다 
@GetMapping("/board/write")   // 주소창 입력 → 폼 화면 반환
public String boardWriteForm(){ return "boardwrite"; }

@PostMapping("/board/write")  // 폼 제출 → 저장 처리
public String boardWrite(Board board){ ... }
URL은 같지만 전송 방식이 다르면 Spring이 각각 다른 메서드를 실행해. 이미 프로젝트에서 /board/writepro가 POST 방식으로 동작하고 있어.
Step 8

중요도 구분

🔴 반드시 이해

  • URL 파라미터(?id=1)를 메서드 파라미터로 받는 방법
  • model.addAttribute()로 HTML에 데이터 전달하는 구조
  • findById(id)로 특정 데이터 1개를 조회하는 방법

🟡 개념만 이해

  • Optional — 값이 있을 수도 없을 수도 있는 컨테이너
  • th:href="@{...}" — Thymeleaf URL 파라미터 문법

🟢 나중에 공부

  • Optional.orElseThrow() — 값 없을 때 예외 처리
  • @RequestParam으로 명시적 파라미터 바인딩
  • @PathVariable — /board/view/1 스타일 URL
Step 9

오늘 배운 것

  • @GetMapping 메서드에서 URL 파라미터를 메서드 파라미터로 그냥 받을 수 있다 (Integer id). Spring이 문자열 → 타입 변환까지 자동으로 해준다.
  • 메서드 파라미터 순서는 상관없다. Spring이 이름과 타입으로 주입하기 때문이다.
  • model.addAttribute("키", 값)으로 Controller에서 HTML로 데이터를 전달한다.
  • Optional은 Java 클래스로, 값이 있을 수도 없을 수도 있는 상자다. null과 다르다.
  • findById()는 Optional을 반환하고 .get()으로 실제 객체를 꺼낸다. 값이 없으면 에러 발생.
  • save(), findAll(), findById(), deleteById()는 각각 반환 타입이 다르다. findById()만 Optional이다.
  • save()는 DB가 생성한 id가 채워진 Board 객체를 반환한다.
  • 에러 처리는 Service에서 던지고 @ControllerAdvice 전역 핸들러에서 잡는 구조가 일반적이다.
  • GET/POST는 URL의 ?가 아니라 @GetMapping/@PostMapping으로 결정된다. 같은 URL도 전송 방식이 다르면 다른 메서드가 실행된다.
  • Thymeleaf에서 th:href="@{경로(파라미터=값)}" 문법으로 URL을 동적으로 만든다. URL 인코딩도 자동 처리된다.
Step 10

이해도 확인 질문

  1. /board/view?id=3 요청이 오면 Integer id에 어떤 값이 들어오는가?

    3이 들어온다. Spring이 URL 파라미터 이름과 메서드 파라미터 이름이 같으면 자동으로 값을 넣어준다.

  2. model.addAttribute("board", board)에서 첫 번째 인자 "board"의 역할은?

    HTML에서 데이터를 꺼낼 때 사용하는 이름(키)이다. HTML에서 ${board.title}처럼 이 이름으로 접근한다.

  3. findAll()과 findById()의 차이는?

    findAll()은 테이블의 모든 행을 List로 가져오고, findById()는 PK로 딱 1개의 행을 Optional로 가져온다. JPA가 자동으로 SQL을 만들어 실행한다.

  4. findById(id).get()에서 .get()을 반드시 써야 하는 이유는?

    findById()의 반환 타입이 Optional<Board>이기 때문이다. Optional은 껍데기이고 실제 Board 객체를 꺼내려면 .get()을 호출해야 한다.

  5. boardlist.html에서 th:href="@{/board/view(id=${board.id})}"가 만들어내는 실제 URL은?

    board.id가 1이면 /board/view?id=1, 2이면 /board/view?id=2 가 된다. th:each 루프를 돌면서 각 게시글마다 다른 id로 URL이 생성된다.

Step 12

다음 Commit을 위한 준비

  • 게시글 수정 — 상세 페이지에서 수정 버튼을 누르면 수정 폼이 열리고, 저장하면 DB가 업데이트되는 흐름
  • 게시글 삭제 — 특정 id의 게시글을 DB에서 삭제하는 deleteById() 메서드
  • JPA의 save() — id가 없으면 insert, 있으면 update로 동작 (수정 기능의 핵심)
  • @PathVariable — ?id=1 대신 /board/view/1 같은 URL 스타일로 파라미터를 받는 방법
  • 예외 처리 — 존재하지 않는 id로 접근했을 때 에러 페이지를 보여주는 방법
