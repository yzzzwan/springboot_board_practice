Step 1

이번 Commit 한눈에 보기

이번에는 큰 기능 하나가 아니라, 이미 만들어둔 파일 업로드 기능을 실무 수준으로 다듬는 네 번의 작은 커밋이 이어졌습니다.

첫 번째 커밋에서는 화면에 보여줄 원본 파일명과 실제로 디스크에 저장되는 파일명을 분리하고, 게시글 id별로 폴더를 나누던 구조도 없앴습니다.
두 번째 커밋에서는 파일을 다시 올려서 기존 파일을 교체할 때, 이전 파일이 디스크에 그대로 남아있던 문제(고아 파일)를 정리했습니다.

세 번째 커밋에서는 게시글을 삭제할 때 DB row만 지워지고 첨부파일은 디스크에 남아있던 문제를 고쳤습니다.
마지막 커밋에서는 아무 확장자의 파일이나 업로드할 수 있던 문제를 막기 위해 확장자 화이트리스트 검사를 추가했습니다.

네 커밋 모두 "파일을 다루는 코드가 실제 서비스에서 안전하게 동작하려면 무엇을 더 신경 써야 하는가"라는 하나의 질문으로 이어집니다.

BoardService.java — 파일 저장/삭제 로직 전면 정리

BoardService.java

private String projectPath = System.getProperty("user.dir") + "\\src\\main\\resources\\static\\files";

public void boardWrite(Board board, MultipartFile file) throws Exception{
    String prevFileName = board.getFilename();
    if(!file.isEmpty()){
        UUID uuid = UUID.randomUUID();
        String originalFileName = file.getOriginalFilename();
        String fileName = uuid + "_" + file.getOriginalFilename();

        if(!checkFileExtension(fileName)){
            throw new IllegalArgumentException("허용되지 않는 파일 확장자입니다.");
        }

        File saveFile = new File(projectPath, fileName);
        file.transferTo(saveFile);

        board.setOriginal_filename(originalFileName);
        board.setFilename(fileName);
        board.setFilepath("/files/" + fileName);
    }

    boardRepository.save(board);

    if(!file.isEmpty() && StringUtils.hasText(prevFileName)) {
        Files.deleteIfExists(Path.of(projectPath, prevFileName));
    }
}

public void boardDelete(Integer id) throws Exception{
    Board board = boardView(id);
    boardRepository.deleteById(id);

    if(StringUtils.hasText(board.getFilename())) {
        Files.deleteIfExists(Path.of(projectPath, board.getFilename()));
    }
}

public boolean checkFileExtension(String filename){
    String extension = filename.substring(filename.lastIndexOf(".") + 1).toLowerCase();
    if(Set.of("txt", "jpg", "png", "jfif").contains(extension)) return true;
    else return false;
}
  • 어떤 파일? 비즈니스 로직을 담당하는 서비스 계층
  • 왜 이렇게 커졌나? 네 커밋 모두 결국 이 파일의 boardWrite()/boardDelete()를 조금씩 안전하게 다듬는 작업이었기 때문
  • 연결: BoardController가 호출하고, 결과에 따라 예외를 던지면 컨트롤러가 잡아서 화면에 메시지로 보여줌

Step 3

핵심 코드 설명

왜 원본 파일명과 저장 파일명을 나누는가

Board.java

private String original_filename;   // 화면 표시용 (예: minions.jfif)
private String filename;            // 디스크 저장용 (예: b283222f-...-minions.jfif)

초보자 관점

같은 파일이라도 "사람이 보기 좋은 이름"과 "컴퓨터가 안전하게 관리하기 좋은 이름"은 다를 수 있습니다. 그래서 아예 필드를 두 개로 나눴습니다.

Java 관점

두 필드는 똑같은 String 타입이지만 서로 다른 값을 담습니다. original_filename은 사용자가 올린 그대로, filename은 UUID + "_" + 원본이름 형태입니다.

설계 관점

같은 이름의 파일을 여러 사람이 올려도 filename은 uuid 덕분에 절대 겹치지 않습니다. 반면 사용자에게는 uuid가 붙은 지저분한 이름 대신 original_filename을 보여줘서, "저장의 안전성"과 "화면 표시의 가독성"을 동시에 만족시킵니다.

덮어쓰기 전에 값을 미리 확보해두기 — prevFileName

BoardService.java

String prevFileName = board.getFilename();   // (1) 아직 덮어쓰기 전 — "이전" 값
if(!file.isEmpty()){
    ...
    board.setFilename(fileName);             // (2) 이 시점에 새 값으로 덮어씀
    ...
}

초보자 관점

board.setFilename(fileName)이 실행되고 나면, board.getFilename()을 다시 불러도 예전 값은 이미 사라지고 없습니다. 그래서 "예전 값이 필요할 것 같다"면 덮어쓰기 이전에 미리 다른 변수에 담아둬야 합니다.

Java 관점

prevFileName은 board.getFilename()이 리턴한 String 값의 복사본을 담고 있을 뿐이라, 이후 board의 필드가 바뀌어도 prevFileName은 영향을 받지 않습니다.

이전 파일은 DB 저장이 끝난 뒤에만 지운다

BoardService.java

boardRepository.save(board);

if(!file.isEmpty() && StringUtils.hasText(prevFileName)) {
    Files.deleteIfExists(Path.of(projectPath, prevFileName));
}

초보자 관점

파일 삭제는 되돌릴 수 없는 작업입니다. 만약 DB 저장이 실패했는데 파일부터 지워버리면, DB는 여전히 옛날 파일을 가리키는데 그 파일은 이미 없는 상태가 되어 다운로드 링크가 깨집니다.

설계 관점

그래서 순서가 중요합니다. 1) 새 파일 저장 → 2) DB 저장 성공 확인 → 3) 그제서야 이전 파일 삭제. !file.isEmpty() 조건을 저장 전후로 두 번 검사하는 비용은 아주 작지만, 이 순서 덕분에 DB 저장이 실패했을 때 삭제 코드 자체가 실행되지 않아 데이터가 안전합니다.

게시글을 지우기 전에 먼저 조회해서 파일명을 확보한다

BoardService.java

public void boardDelete(Integer id) throws Exception{
    Board board = boardView(id);           // (1) 지우기 전에 먼저 조회
    boardRepository.deleteById(id);        // (2) DB row 삭제

    if(StringUtils.hasText(board.getFilename())) {
        Files.deleteIfExists(Path.of(projectPath, board.getFilename()));  // (3) 파일 삭제
    }
}

초보자 관점

boardRepository.deleteById(id)를 먼저 해버리면, 그 게시글이 어떤 파일을 가지고 있었는지 알 방법이 사라집니다. 그래서 지우기 전에 boardView(id)로 먼저 조회해서 파일명을 변수에 담아둬야 합니다.

바로 위에서 배운 prevFileName과 완전히 같은 원리입니다 — "사라질 값은 사라지기 전에 먼저 읽어둔다."

확장자 검사와 예외 던지기

BoardService.java

if(!checkFileExtension(fileName)){
    throw new IllegalArgumentException("허용되지 않는 파일 확장자입니다.");
}

public boolean checkFileExtension(String filename){
    String extension = filename.substring(filename.lastIndexOf(".") + 1).toLowerCase();
    if(Set.of("txt", "jpg", "png", "jfif").contains(extension)) return true;
    else return false;
}

초보자 관점

허용된 확장자 목록(Set)에 없는 파일이 들어오면, 그냥 조용히 넘어가지 않고 "이건 문제가 있는 입력이다"라고 예외를 던져서 알립니다.

Java 관점

IllegalArgumentException은 RuntimeException의 한 종류라 unchecked 예외입니다. 지난 시간에 배운 Files.deleteIfExists()의 IOException(checked 예외)과 대조됩니다. IOException은 "디스크 장애처럼 코드로 막을 수 없는 문제"에 붙는 반면, IllegalArgumentException은 "호출한 쪽이 잘못된 값을 넘겼다"는 의미로 자바 표준 라이브러리에서도 널리 쓰입니다.

⭐ 현업 포인트

확장자만 검사하는 지금 방식은 1차 방어선일 뿐입니다. 파일 확장자는 사용자가 파일명을 바꾸기만 하면 얼마든지 위조할 수 있기 때문입니다 (예: malware.exe → malware.jpg).

실무에서는 파일의 실제 내용(맨 앞 몇 바이트, 매직 바이트)을 읽어서 진짜 이미지/문서 형식이 맞는지 확인합니다 (Apache Tika 같은 라이브러리, 또는 Files.probeContentType()). 지금은 화이트리스트 검사만으로도 충분한 학습 단계이지만, "왜 이게 완벽한 보안이 아닌지"는 기억해두면 좋습니다.

💡 개선 포인트

파일명에 점(.)이 아예 없는 경우(filename.lastIndexOf(".")가 -1)를 아직 처리하지 않고 있습니다. 이 경우 substring(0)이 호출되어 파일명 전체가 extension 변수에 들어가고, 당연히 허용 목록에 없으니 결과적으로 false(거부)가 되긴 하지만, "확장자가 없다"는 것과 "확장자가 이상하다"는 것을 구분하고 싶다면 dotIndex == -1을 먼저 체크하는 분기를 추가하면 더 명확해집니다.

Step 4

왜 이렇게 작성했는가?

왜 별도 테이블 대신 Board에 필드 하나만 추가했는가

원본 파일명을 저장할 곳이 필요할 때, 실무라면 Attachment 같은 별도 엔티티로 분리하는 경우가 많습니다. 하지만 지금 프로젝트는 게시글 하나에 파일 하나만 첨부하는 구조라서, Board에 필드 하나(original_filename) 추가하는 것으로 충분합니다. 나중에 "게시글 하나에 파일 여러 개" 요구사항이 생기면 그때 별도 테이블로 확장하면 됩니다.

왜 파일 삭제 코드를 save() 다음으로 옮겼는가

파일 삭제는 되돌릴 수 없는 작업입니다. 반면 DB 저장은 실패할 수도 있는 작업입니다. 되돌릴 수 없는 작업은 항상 "확실히 성공한 것을 확인한 뒤에" 실행해야, 중간에 실패했을 때 시스템이 어중간한 상태(DB는 옛날 파일을 가리키는데 그 파일은 이미 삭제된 상태)에 빠지지 않습니다.

왜 확장자 오류엔 checked Exception이 아니라 unchecked Exception을 던지는가

boardWrite()는 이미 throws Exception이 붙어있어서 checked 예외를 던져도 컴파일은 됩니다. 하지만 Exception을 그대로 던지면 나중에 컨트롤러에서 "이게 파일 문제인지, 디스크 문제인지, 다른 문제인지" 구분해서 잡을 수 없습니다. IllegalArgumentException처럼 의미가 명확한 예외를 던지면, 컨트롤러에서 catch (IllegalArgumentException e)로 정확히 이 상황만 골라서 사용자에게 안내할 수 있습니다.

왜 컨트롤러에서 예외를 잡아 메시지로 보여주는가

제목/내용을 비워뒀을 때 이미 StringUtils.hasText()로 검증하고 message.html로 안내하는 패턴이 있었습니다. 확장자 검증도 "사용자 입력이 잘못됐다"는 점에서 성격이 같기 때문에, 같은 사용자 경험(안내 메시지 화면)으로 통일한 것입니다. 다만 확장자 검사는 파일명을 조합하는 서비스 로직 한가운데서 이뤄지기 때문에, 제목/내용처럼 컨트롤러에서 미리 걸러내기보다 예외 + try-catch 방식이 더 자연스럽습니다.

초보자가 하기 쉬운 착각

변수를 미리 캡처해두면 그걸로 끝이라고 착각하기 쉽다

prevFileName을 덮어쓰기 전에 잘 저장해뒀더라도, 정작 삭제하는 줄에서 board.getFilename()(새 값)을 다시 불러버리면 아무 의미가 없습니다.

"올바른 변수를 만드는 것"과 "그 변수를 실제로 사용하는 것"은 별개의 실수 포인트입니다. 실제로 이번 기능을 만드는 과정에서도 이 실수가 두 번이나 반복됐습니다.

Files.deleteIfExists()가 폴더 안의 파일까지 재귀적으로 지워준다고 착각하기 쉽다

Files.deleteIfExists(Path.of(projectPath))처럼 파일명 없이 폴더 경로만 넘기면, 그 폴더 자체를 지우려는 시도가 됩니다. 폴더 안에 파일이 있으면 오히려 삭제에 실패(예외)합니다. 재귀 삭제 기능은 아예 없습니다.

확장자만 막으면 보안이 완성됐다고 착각하기 쉽다

확장자는 파일명 문자열일 뿐이라 얼마든지 위조할 수 있습니다. 지금 단계에서는 화이트리스트 검사만으로 충분하지만, "이걸로 다 막았다"고 생각하면 안 됩니다.

Step 9

오늘 배운 것

  • 필드를 덮어쓰기 전에 이전 값을 별도 변수에 담아두면, 나중에 "이전 상태"를 참조할 수 있다.
  • 파일 삭제처럼 되돌릴 수 없는 작업은 DB 저장이 확정된 뒤에 실행해야 안전하다.
  • 화면 표시용 값(original_filename)과 저장/식별용 값(filename)을 분리하면 안전성과 가독성을 동시에 챙길 수 있다.
  • Files.deleteIfExists()는 파일 하나 또는 빈 디렉토리만 지울 수 있고, 재귀 삭제 기능은 없다.
  • checked 예외는 코드로 막을 수 없는 문제에, unchecked 예외는 잘못된 입력값에 사용한다.
  • 확장자 검사는 첫 번째 방어선일 뿐, 실무에서는 파일 내용까지 검증한다.
Step 10

이해도 확인 질문

클릭해서 정답을 확인하세요.

  1. prevFileName 변수를 만들어뒀는데도 실제로는 "새로 올린 파일"이 지워지는 실수가 발생했습니다. 왜 그럴까요?

    변수를 캡처해두는 시점(덮어쓰기 전)은 맞았지만, 실제로 삭제할 때 그 변수(prevFileName) 대신 이미 새 값으로 바뀐 board.getFilename()을 다시 참조했기 때문입니다. 변수를 올바르게 만드는 것과 실제 사용하는 곳에서 그 변수를 쓰는 것은 별개의 문제입니다.

  2. 이전 파일을 지우는 코드를 boardRepository.save(board) 이후로 옮긴 이유는 무엇인가요?

    파일 삭제는 되돌릴 수 없는 작업이기 때문입니다. save()가 실패할 수도 있는데, 저장 전에 파일부터 지우면 DB는 옛날 파일을 가리키는데 그 파일은 이미 삭제된 상태가 되어 데이터가 깨집니다. 저장이 성공한 것을 확인한 뒤에 지워야 안전합니다.

  3. Files.deleteIfExists(Path.of(projectPath))처럼 파일명 없이 폴더 경로만 넘기면 폴더 안의 파일이 다 지워지나요?

    아닙니다. deleteIfExists는 넘겨받은 경로 하나만 대상으로 합니다. 그 경로가 폴더이고 안에 파일이 있으면 오히려 삭제에 실패(DirectoryNotEmptyException)합니다. 재귀적으로 안의 파일들을 지우는 기능은 없습니다.

  4. IOException과 IllegalArgumentException을 구분해서 쓰는 기준은 무엇인가요?

    IOException은 디스크 용량 부족, 권한 없음처럼 코드로 막을 수 없는 외부 요인에 의한 실패에 사용하는 checked 예외입니다. IllegalArgumentException은 호출한 쪽이 애초에 잘못된 값(예: 허용 안 된 확장자)을 넘겼을 때 사용하는 unchecked 예외입니다.

Step 11

작은 실습

실습: 확장자가 없는 파일명 처리하기

checkFileExtension()은 파일명에 점(.)이 아예 없는 경우를 아직 명시적으로 처리하지 않습니다. lastIndexOf(".")가 -1인 경우를 먼저 걸러내는 분기를 추가해보세요.

public boolean checkFileExtension(String filename){
    int dotIndex = filename.lastIndexOf(".");
    if(dotIndex == -1) return false;   // 여기부터 직접 채워보기

    String extension = filename.substring(dotIndex + 1).toLowerCase();
    return Set.of("txt", "jpg", "png", "jfif").contains(extension);
}

힌트:

  • 지금도 결과적으로는 false가 나오지만, "확장자가 없다"와 "확장자가 허용되지 않는다"는 의미가 다릅니다.
  • 메시지를 구분해서 보여주고 싶다면 IllegalArgumentException의 메시지도 상황에 따라 다르게 던져보세요.
